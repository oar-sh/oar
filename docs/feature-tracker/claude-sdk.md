# Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`)

Updated: 2026-08-17 · Part of the [SDK Feature Tracker](README.md) — legend, changelog, and
provider-agnostic relay rows live there.

Everything below lives in `server/claude-worker/` unless noted. The SDK has exactly two import
sites: `claude-sdk-adapter.mjs` (the worker's single static import — the turn-path surface is
auditable from that one file) and a deliberate dynamic `import()` in `server/server-runtime.mjs`
used only for model discovery (`refreshClaudeProviderModels`).

Authentication uses the relay host's logged-in Claude credentials; the relay stores no API key.

## Turn execution

| SDK feature | Status | Notes / evidence |
| ----------- | ------ | ---------------- |
| `query()` streaming-input mode | Implemented | One persistent query per conversation: the user-message stream is *pushable* — later relay turns are fed into the same live CLI process via `turn.pushUserMessage`, and the stream only ends (`turn.endInput`) when the session process winds down (idle, recycle, shutdown). This is what lets background tasks and their continuation turns outlive individual replies (`claude-sdk-adapter.mjs` → `startClaudeSession`, `createPushableUserMessageStream`; lifecycle in `claude-session-process.mjs`). |
| `options.resume` | Implemented | The native session id from the first turn is persisted (POST `/api/claude-native-session`, cached only after server ack) and replayed, so a conversation survives worker restarts (`claude-session-process.mjs` → `persistNativeSessionId`). |
| `options.model` (per turn) | Implemented | Per-message model wins only when non-`auto` **and** `claude-`-prefixed; conversation provider model and worker default (`CLAUDE_RELAY_MODEL`) are fallbacks (`claude-session-process.mjs`). |
| `options.effort` (per turn) | Implemented | `normalizeClaudeEffort` whitelists `low/medium/high/xhigh/max` plus the relay sentinel `ultracode`; `none` (and any unknown value) maps to "omit the option" — the SDK default (`claude-sdk-adapter.mjs`). |
| `options.settings` (ultracode) | Implemented (2026-08-17) | `ultracode` is **not** an SDK `EffortLevel` — it is a session-scoped settings flag, so the relay carries it as a sentinel on the normal effort ladder and only the worker translates it. Spawn sends `effort: 'xhigh'` + `settings: { ultracode: true, enableWorkflows: true }`; `enableWorkflows` is explicit because the worker loads no filesystem settings. The tier is *derived*, not discovered — `withClaudeUltracodeTier` appends it to any model whose discovered efforts include `xhigh` (`server/services/provider-reasoning-effort.mjs`, the single Claude effort ladder). Never a silent default. (`claude-sdk-adapter.mjs` → `CLAUDE_ULTRACODE_EFFORT`, `startClaudeSession`.) |
| `options.permissionMode` | Partial | Only `plan` (relay `plan` mode) and `default` are used; `acceptEdits` / `bypassPermissions` are not wired (`claude-sdk-adapter.mjs` → `permissionModeForRelayMode`). |
| `options.systemPrompt` (preset+append) | Implemented | `claude_code` preset with a mode-specific append for `ask` and `autopilot` (`claude-sdk-adapter.mjs` → `systemPromptForRelayMode`). |
| `options.includePartialMessages` | Implemented | Drives live reply streaming and thought streaming (`claude-sdk-adapter.mjs`, `sdk-message-normalizer.mjs`). |
| `options.forwardSubagentText` | Implemented | Subagent text is forwarded and routed to its own bubble by `subagentRunId` (derived from `parent_tool_use_id`); main-thread text is tracked separately so subagent prose can never be published as the reply. |
| `options.abortController` | Implemented | Backs the relay Stop control, driven by the control poller (`control-poller.mjs`, `claude-session-process.mjs` — abort maps to `query.interrupt()` so the persistent process survives). |
| `options.cwd` | Implemented | Set from `COPILOT_WORKSPACE_ROOT` (`claude-session-worker.mjs`). |
| `options.pathToClaudeCodeExecutable` | Implemented | Set from `CLAUDE_CODE_EXECUTABLE` when provided. |
| `options.maxTurns` | Not implemented | Turn length is bounded by the relay's own inactivity window (`DEFAULT_PROCESSING_TIMEOUT_MS`, explicitly not a cap on turn length) and the max-turn-duration ceiling (`shared/turn-ceiling.mjs`, applied in `recoverStaleMessages`) instead. |
| Image content blocks | Implemented | Only the media types the Anthropic image block accepts (jpeg/png/gif/webp) inline, ≤ 5 MB on BOTH the file-read and data-URL paths (the fallback used to bypass the cap); everything else — oversized, exotic type, unresolvable — becomes a visible path/failure note; non-image files become absolute path references for the `Read` tool (`claude-attachments.mjs`). |

## Control requests + tools

| SDK feature | Status | Notes / evidence |
| ----------- | ------ | ---------------- |
| `canUseTool` | Partial | Everything is auto-allowed (parity with the Copilot workers' `--allow-all`); only `AskUserQuestion` and `ExitPlanMode` are intercepted, and a bridge failure returns `behavior: 'deny'` with a message (`claude-sdk-adapter.mjs` → `createCanUseTool`). |
| `AskUserQuestion` tool | Implemented | Bridged to relay question cards, one card per question entry, returning the collected `answers` map as `updatedInput` (`ask-user-bridge.mjs`). |
| `ExitPlanMode` tool | Implemented | Publishes a `plan_ready` relay board (`source: exit_plan_mode`); a heuristic fallback also posts one when a `plan`-mode turn ends with ≥2 plan-shaped lines but never called the tool (`claude-turn-publisher.mjs` → `countPlanLikeLines`, `source: plan-mode-fallback`). |
| `query.supportedModels()` | Implemented | Model discovery via a short-lived idle query (never-yielding gated prompt, `cwd: os.tmpdir()`) with a 20 s timeout; keeps explicit `claude-*` ids (a trailing `[…]` suffix like `[1m]` survives `isSafeClaudeModelId`), drops bare aliases, and harvests `supportedEffortLevels` per model (`server/server-runtime.mjs` → `refreshClaudeProviderModels`, `shared/model-id.mjs`). |
| `query.getContextUsage()` | Implemented | Read from inside the message loop while the transport is still open (10 s timeout), normalized by `server/services/claude-context-usage.mjs` (`buildClaudeContextSnapshot`, context window from `modelUsage[model].contextWindow`), and posted to the relay on every exit path (`claude-sdk-adapter.mjs` → `readContextUsage`, `claude-turn-publisher.mjs` → `publishContextUsage`). `autoCompactThreshold` is a **token count**, not a percent (measured: opus-5 1000000/967000, sonnet-5 967000/934000, haiku 200000/167000); reading it as a percent made `buffer_tokens` clamp to 0 for every real payload. `rawMaxTokens` (**not** the model's own limit — probed on `claude-opus-5[1m]`, it tracks the active window setting: no setting → 1000000, setting 100000 → 100000, so nothing may annotate the window slider from it) and `autocompactSource` (`auto` | `model-default` | settings | env) are carried too — the latter is what tells you *why* a session has the window it has. |
| `query.setMaxThinkingTokens()` | Implemented (2026-08-26) | The **display axis** of the per-conversation thinking control (`conversations.thinking_display`, context-modal buttons, delivered on the queue-settings piggyback): `summarized` (**the relay default**) or `omitted`. Display is visibility only — the model thinks and bills identically either way, so hiding is not a cost control. The deprecation is on the FIRST argument only; the second (`thinkingDisplay`) has no replacement on a live session and is the sole live display lever. **The call is load-bearing**: probed 2026-08-26, the API default on current models hides thinking text (blocks arrive with `thinking: ''`), so without it there are no thought bubbles at all. The budget argument is positional and re-sent from a tracked value (`proc.thinkingBudget`, always null today) rather than hardcoded — a hardcoded null would silently clear any future budget pin on every display change. Applies live in both directions and survives `setModel()`; re-asserted (settings-first order) whenever thinking is enabled live, because a session spawned with thinking off carries no display mode. Best-effort on old CLIs (`claude-sdk-adapter.mjs` → `applyThinkingDisplay`, reconciled in `claude-session-process.mjs` → `adaptProcess`). The budget axis stays deliberately out of scope: deprecated, and probed to be no off-switch mid-session either (`setMaxThinkingTokens(0, …)` only empties the block's text). |
| `Settings.alwaysThinkingEnabled` | Implemented (2026-08-26), **spawn-scoped off** | The on/off axis of the thinking control (`conversations.thinking_enabled`: NULL = never set → **the relay default, ON**; 1 = on; 0 = off). copilot-remote deliberately takes a position rather than deferring to the CLI, so `alwaysThinkingEnabled` is always sent at spawn. There is no "host default" state on either axis: the worker loads no `settingSources`, so "host" only ever meant the CLI built-in (itself on for supported models), and it could only be stored as SQL NULL — indistinguishable from "never set" once NULL resolves to the default. Probed on CLI 2.1.226: the key is honored at **spawn** in both directions, and mid-session only in the **enabling** direction — `applyFlagSettings({alwaysThinkingEnabled: false})` (or clearing to null) is accepted and **silently ignored**, invisible in the type definitions and rediscoverable only by probe. The worker therefore applies enable live (then re-sends the display), and records disable/revert as a next-spawn request (`proc.thinkingEnabledPending`) without touching `proc.thinkingEnabled` — pretending the CLI obeyed would break the next enable diff. The UI labels the two directions honestly ("next message" vs "applies when the CLI session next restarts"). Interaction with `effort`/`ultracode` under spawn-time off is untested. Model gating via `ModelInfo.supportsAdaptiveThinking` is deferred — the control is a graceful no-op on models without adaptive thinking. (`claude-sdk-adapter.mjs` → `claudeSpawnSettings`/`claudeThinkingFlagSettings`, `shared/claude-thinking.mjs`.) |
| `query.close()` | Implemented | Tears down the discovery query in a `finally`, after releasing the input gate (`server/server-runtime.mjs`). |
| Targeted subagent cancellation | Implemented for backgrounded subagents (2026-08-16) | `task_started`/`task_progress` report the spawning `tool_use_id` — the same identity the relay uses as `subagentRunId` — so `abort_subagent` maps to `query.stopTask()` when the run is a live background task (`claude-session-process.mjs` → `stopBackgroundTaskByToolUseId`, wired via `control-poller.mjs` `onAbortSubagent`). In-turn subagents still answer "not supported" (whole-turn Stop only). |
| `query.interrupt()` | Implemented | The relay Stop control interrupts the current turn instead of killing the persistent process, so background tasks survive a Stop; a failed interrupt falls back to aborting the process (`claude-session-process.mjs` → `interruptActiveTurn`). |
| `query.setModel()` / `setPermissionMode()` / `applyFlagSettings({effortLevel})` | Implemented | Per-turn model, relay-mode permission mode, and reasoning effort are applied to the live process as diffs before each pushed message. Effort goes through `claudeUltracodeFlagSettings` (`claude-sdk-adapter.mjs`), so entering ultracode mid-session sends `{ ultracode: true, enableWorkflows: true, effortLevel: 'xhigh' }` and leaving it clears both flags alongside the newly requested effort — live-verified in both directions on `claude-opus-5`. A relay-mode change that would alter the spawn-time system prompt append recycles the process — but only when nothing (task/turn/question) lives in it (`claude-session-process.mjs` → `adaptProcess`). `autoCompactWindow` reconciles the same way and must send an explicit `null` to return to Auto: successive `applyFlagSettings` calls shallow-merge, and `undefined` is dropped by JSON serialization, so it would leave a pin the user had cleared. |
| `query.stopTask()` | Implemented | Backs the composer panel's per-task Stop button (`worker.control` websocket push → `stopBackgroundTask`) and the background-task timeout expiry (`claude-session-process.mjs`). |

## Message-stream consumption

The relay observes the SDK by normalizing its message stream rather than registering hooks. All of
this lives in `sdk-message-normalizer.mjs`.

| Stream surface | Status | Notes / evidence |
| -------------- | ------ | ---------------- |
| `stream_event` partial messages | Implemented | `normalizeStreamEvent` handles `message_start`, `content_block_start`, `text_delta`, `thinking_delta`, `content_block_stop`; emission is gated (`shouldEmitStreamUpdate`: ≥24-char delta or sentence-ending punctuation) to mirror the Copilot publisher. |
| Stable reasoning ids across partials | Implemented | Ids of the form `claude-{thought\|narration}-{thread}-{msgIndex}-{blockIndex}` are kept stable between partial frames and the complete `assistant` message (`beginAssistantMessage` reconciliation), so the server upserts thoughts instead of duplicating them. |
| Narration demotion | Implemented (rebuilt 2026-08-16 for per-block delivery) | The SDK delivers one complete assistant event per content block (same `message.id`), so tool-bearing is tracked per message: text buffered until a sibling `tool_use` proves it narration, answer text never doubles as a thought, the live stream accumulator resets at each message boundary, and `redacted_thinking` surfaces as a placeholder; thoughts are capped at 16 KiB (`MAX_THOUGHT_CHARS`). |
| Subagent lifecycle inference | Implemented | Tool names in `SUBAGENT_TOOL_NAMES` (`task`/`agent`) open a `running` subagent run keyed by `tool_use.id`; the matching `tool_result` closes it `completed`/`failed`. Purely derived from tool blocks — not an SDK lifecycle API. |
| Tool-failure surfacing | Implemented | `tool_result.is_error` becomes a truncated "Tool failed: …" activity line. |
| `system` / `compact_boundary` | Implemented | Host-driven auto-compaction becomes a full-width break row in the transcript. `compact_metadata.pre_tokens` / `post_tokens` ride the activity as `relay_activity.metadata_json` (`{kind:'compact_boundary', preTokens, postTokens}`) rather than being formatted into prose and discarded, so the row can be promoted out of the collapsed tool-activity details (`sdk-message-normalizer.mjs` → `claude-turn-publisher.mjs` → `POST /api/activity`; rendered by `server/public/app/transcript-separators.mjs`). Structured rows survive the per-turn activity cap (`capRelayActivityEntries`), which previously kept the first 48 entries and so dropped boundaries from long turns. `post_tokens` is optional and **absent from both auto-compact payloads inspected on disk** (conv `563e252e`; never captured off the live stream), so the row degrades to a pre-only label instead of losing its metadata (an omitted count must not read as 0). The boundary is also observed at process level (`claude-session-process.mjs` → `observeProcessLevel`): a compaction at resume — what lowering the window causes — arrives with no turn context, where the per-turn normalizer never sees it, and is buffered onto the next context instead of being dropped (which is why no conversation had ever recorded one). At most one publish either way: the process-level path buffers only when no context would *publish* — a discarded context is still `activeCtx` but drops everything dispatched to it. (A turn whose registration is still in flight buffers the boundary with the rest of its output, so a registration that then fails all three attempts loses the break row along with the whole turn.) The relay never *triggers* compaction (see the README's `/compact` row). |
| `system` / `status` | Implemented | `status: 'compacting'` — emitted **once, at compaction start** (the bundle's 30 s re-emit is gated on the remote-control client's activity callback, which the plain SDK `query()` never registers), released by the boundary or by any later status that is not a permission-mode notice (`{status:null, compact_result}` normally; a BARE `{status:null}` when an early compact start compacts nothing), with a 10-minute staleness cap as the backstop — is the only in-progress signal for work that produces no stream traffic for minutes: it holds the process against idle shutdown and stops the pending-delivered watchdog counting a compaction as idleness. A compaction signal also lets the turn the CLI re-opens afterwards — with its own summary message, whose text matches no delivered entry — be adopted by the delivered message it answers, instead of publishing on a synthetic continuation while the real row orphans (conv `563e252e`, 2026-08-20). Adoption is armed only while a delivered entry waits, is one-shot (the first turn to open spends it), and is never applied mid-turn. Which turn may spend it takes two signals, because the untagged summary row follows *any* compaction. **Which message** this is is tested POSITIVELY: the summary is the CLI's own synthesized replay and carries **no `origin`** (incident transcript row 1514: `origin=None`), so any stamped `SDKMessageOrigin` — the union has nine members (`human`, `peer`, `channel`, `task-notification`, `coordinator`, `unclassified`, …) — disqualifies it, as does an unreadable opening block or the legacy `<task-notification>` tag. Testing for *not* `task-notification` instead would fail open: a cross-session `peer` message would be read as the compaction's summary and steal the row permanently. **Which turn** it belongs to comes from `lastBoundary`: a compaction inside a turn the CLI had already opened for itself adopts nothing. The live-verified no-user-replay continuation shape gets a second, narrower flag (`continuationInitPending`): a mid-session `init` — never the process's first — with a delivered row already waiting. That is structural rather than timed (a delivered turn cannot produce an init: the process is already running, and only a spawn inits), which matters because every freshness-clock variant of this rule failed twice over — the notification grace is 60 s against a 133 s compaction, and `activateContext` zeroes the settle timestamps, so any turn attaching in between erases the signal. It suppresses adoption *only*, and is cleared by the next turn to open a context (`activateContext`); routing it through `lastBoundary` instead would also divert assistant traffic away from a waiting delivered row, failing the user's message over. When both hold the adoption is still **provisional** (`ctx.adoptedFromCompaction`), and is committed only by the turn's first real output — a **top-level** `assistant`, `stream_event` or `result` frame: never a `system` one (the compaction's own `compact_result` status routinely lands between the summary row and what follows), and never a frame carrying `parent_tool_use_id`, which is a live background subagent's chatter rather than this turn's answer. It is also committed by the adopted message's OWN replay — the CLI proving it dequeued exactly that prompt, after which every unwind path would be unsound (they all rest on "the CLI never consumed this"). Until then the row is given back (`restoreAdoptedContext`: queue head, unattached clock reset, control poller stopped) by a task notification replaying into the same turn (which then registers its own continuation), by a phantom result, by a steering absorption (whose "merged into the next message" settle must never be applied to a prompt the CLI has not consumed — and which must not pass its normalizer to the displacing turn, or the restored row would later publish that turn's streamed text as its own answer), and by `reapSilentProvisionalAdoption` when the turn produces nothing at all. That last one matters because adoption splices the entry out of `pendingDelivered`, i.e. out of the watchdog's reach: without it a silent turn would pin the process on an inference forever, which is worse than the orphan it replaced. Four successive designs that instead tracked what the CLI was *owed* (a freshness clock, a boolean latch, a per-task ledger, tag sniffing alone) each mis-accounted in one direction or the other. |
| `system` / `task_notification` | Implemented | Background-task notifications become activity lines ("Background task <id> <status>: <summary>") plus a `background_task_settled` edge action. In the persistent-process runner a settled session-level task pins the process for its continuation turn (60 s grace covers silent `skip_transcript` notifications); notifications that arrive between turns are buffered and attached to the turn they trigger. |
| `system` / `background_tasks_changed` | Implemented | One persistent CLI process per conversation (`claude-session-process.mjs`, streaming input): the live task set (REPLACE semantics, ALL task types including `local_bash` — the old bash exclusion killed finite E2E runs seconds after the reply, incident conv `2353a9eb`) keeps the process alive across turns, so "you will be notified" actually happens. Continuation turns the CLI dequeues on its own publish as separate relay turns via `POST /api/continuation-turn` (synthetic owned queue rows, `kind='continuation'`, never deliverable/requeued). The set is forwarded to `POST /api/background-tasks` (enriched from `task_started`/`task_progress`) for the composer panel, which can stop tasks via `stopTask()` over a `worker.control` push. Lifecycle: idle shutdown (default 10 min, `CLAUDE_RELAY_IDLE_SHUTDOWN_MS`) when no turn/task/question is live; the "Background task timeout" slider (0 = no limit, default) caps task-only holds; abort-turn maps to `interrupt()` so the process and its tasks survive a Stop. `local_workflow` rows additionally carry a live `workflowProgress` digest (see the on-disk artifacts table) that the panel folds out as a phase/agent tree. When such a task settles the worker buffers its final digest (`bufferSettledWorkflowRun`, ≤5, terminal status never downgraded — the SDK usually drops the task row *before* the `task_notification`, so `refineSettledWorkflowStatus` upgrades it when the late notification lands) and `drainSettledWorkflowRuns` attaches it to the next `POST /api/response` as `workflowRuns`, retrying the run-record read for runs that settled on a journal snapshot because the CLI often flushes the record seconds late. The relay persists those per response message (`workflow_runs`) and the transcript renders a collapsed "Finished background task" card from the same tree renderer. |
| Phantom zero-work result skip | Implemented | A resumed session whose previous CLI process died with tracked background tasks replays a bookkeeping turn that emits a `success` result with `num_turns === 0 && duration_api_ms === 0` *before* the real turn. It is dropped at both the normalizer and the session process level, so it can neither stand in for a delivered turn's result nor open a phantom continuation turn. |
| `result` usage fields | Implemented | `modelUsage` (per-model `contextWindow`, used as fallback when `getContextUsage()` is unavailable) and `total_cost_usd` are carried on the normalized result. |
| Turn error classification | Implemented | Auth-shaped errors become `claude.authentication_failed` with a "run `claude` on the relay host" message; other failures map to `claude.turn-error` / `claude.<result.subtype>` (`claude-session-process.mjs`). |

## SDK on-disk artifacts

| Surface | Status | Notes / evidence |
| ------- | ------ | ---------------- |
| Workflow journal + run record | Implemented (2026-08-17) | The CLI has no SDK surface for workflow progress, so the worker reads it off disk under the resolved session dir: `subagents/workflows/<runId>/journal.jsonl` drives the live view and `workflows/<runId>.json` (the run record, written **only at completion** — verified by probe) takes over as the authoritative labeled tree. Parsed into a clamped digest by `workflow-progress-digest.mjs` (`digestFromJournal`, `digestFromRunRecord`, `stripCommonPromptPrefix`); polled at 2 s only while a `local_workflow` task is live (`claude-session-process.mjs` → `syncWorkflowPoller`, `buildWorkflowDigest`), joined to its task via the record's `taskId` with an mtime-window fallback mid-run, and guarded by a filename pattern plus byte caps on every read. The digest rides the normal task row as `task.workflowProgress`; the relay re-clamps it independently in `sanitizeWorkflowProgress` (`server/routes/messages-routes.mjs`) before store/broadcast. |
| Session root / transcript resolution | Implemented | `server/services/claude-session-root-service.mjs` probes `$CLAUDE_CONFIG_DIR/projects` and `~/.claude/projects`, computes the project-dir slug from the cwd (`claudeProjectDirSlug`), and anchors a session on the `<nativeSessionId>.jsonl` transcript rather than the lazily created `<nativeSessionId>/` directory (which only appears once `subagents/` or `tool-results/` exist). Includes a bounded non-recursive scan fallback for slug misses, a `SESSION_ID_PATTERN` path-injection guard, and hit/miss caches with TTL for ~1 Hz client polling. Consumed via `server-runtime.mjs` → `sessions-routes.mjs`. |

## Session configuration not wired

| SDK feature | Status | Notes |
| ----------- | ------ | ----- |
| `options.hooks` | Not implemented | Relay observation is done by normalizing the SDK message stream instead (`sdk-message-normalizer.mjs`). |
| `options.mcpServers` | Not implemented | No relay-supplied MCP servers; the host's own configuration applies. |
| `options.agents` / custom subagent definitions | Not implemented | Subagents are observed, not defined, by the relay. |
| `options.allowedTools` / `disallowedTools` | Not implemented | Tool gating is handled entirely in `canUseTool`. |
| `options.settingSources` / skills / plugins | Not implemented | Not configured by the worker. |
| `options.thinking` | Not implemented | Deliberate: every variant forces a `type`, which would override the host's own thinking settings — the settings key (`alwaysThinkingEnabled`, see the control-requests table) covers the same on/off ground without that, and the host-default state stays expressible by omission. Probed working (2026-08-26: `{type:'disabled'}` and `{type:'adaptive', display}` both take effect at spawn), so it is a viable fallback if the settings key is ever dropped. |
| `options.fallbackModel` | Not implemented | Not configured by the worker. |
| SDK-native compaction | Partial (2026-08-20) | The relay still never *triggers* compaction — the `/compact` workflow is provider-agnostic (see [README](README.md)). It now *configures* it: `Settings.autoCompactWindow` is a per-conversation setting (`conversations.auto_compact_window`, snapped to stops by `shared/auto-compact-window.mjs`; NULL = Auto), delivered on the normal queue-settings piggyback and reconciled onto the live process. Left unimplemented: `autoCompactEnabled` (no off switch) and any manual trigger. **The CLI enforces a 100k floor** — probed 2026-08-20 on `claude-opus-5[1m]`, a 50k or 60k setting is *dropped* (the resolved window stays 1M with source `auto`) while 100k resolves to source `settings`; the slider's stops therefore start at 100k. |
