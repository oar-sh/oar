# Troubleshooting

Symptoms and what to check. This is the detail behind the [README](../README.md#troubleshooting); the most complete guide is [Troubleshooting on oar.sh](https://oar.sh/docs/troubleshooting/).

| Symptom                            | What to check                                                                    |
| ---------------------------------- | -------------------------------------------------------------------------------- |
| Banner says *CLI is offline*       | No session worker has reported in during the last 10 seconds, which can be normal on an idle relay. Send a message: the relay starts that conversation's worker, and the banner clears once it connects. If it stays, check `/api/status` and the worker's `worker-<session>.log` in the log directory |
| `oar copilot` says the GitHub CLI is missing | It runs `gh copilot` beside the relay. Install the GitHub CLI, or [run only the relay](install.md#start-the-relay) |
| WSL: the browser on Windows shows another relay, or refuses the token | In WSL's default networking a port can be free in the distro while a Windows program listens on it; `localhost:<port>` in a Windows browser then reaches that program. `oar setup` picks a port that is free on both sides, and `oar status`, `oar start` and `oar doctor` warn when Windows holds the relay's port: choose another with `oar setup --port <port>` |
| Settings refuses the **SDK** engine | Install or upgrade the Copilot CLI, run `copilot` once, and restart the relay (see [engine choice](providers.md#github-copilot--engine-choice)) |
| Messages stuck pending             | Only one relay may run per data directory (a second one exits on the singleton lock), and only one process may own port `3333`. `oar doctor` shows the config and database in use |
| Messages to one conversation stay queued after a relay restart | Its worker reconnects by itself, retrying every 8 seconds at most. Its `worker-<session>.log` shows a `worker ws disconnected <reason>` line per failed attempt (the first three, then one a minute), which says why it cannot connect. **☠️ Kill session** in the **︙** menu starts a new worker |
| Wrong or old model list            | **🤗 Select Models → Refresh** reruns discovery; `/api/model-variants` shows the Copilot catalog's `source` and `refreshedAt` |
| A send says *This conversation's model … is no longer available* | The model the conversation was set to has left the Copilot catalog, and the send named no model of its own. Pick a model in the composer's **⚙** settings and send again; the relay no longer switches such a conversation to another model by itself |
| The mode, model and effort selects or the billing toggle are gone from the composer, or a header button such as 🔍 or 📍 is missing | The composer's settings sit behind **⚙** and the label beside it (see [The composer](web-ui.md#the-composer)); header buttons that do not fit move into the **︙** menu (see [The conversation menu](web-ui.md#the-conversation-menu)) |
| Clarification card not progressing | Answer via the web card; the turn resumes once the question status becomes `answered` |
| A Claude session waits on a **Safety check** card for a file such as `.bashrc`, `.npmrc`, or one under `.git/` or `.claude/`, even in autopilot | Claude Code marks the file as sensitive, and only you can approve such an edit, once, in any mode (see [Security notes](security.md)). Check the file and the change on the card, then **Allow once** or **Deny**; the next edit of such a file asks again. A change over 8000 characters is refused without a card, and the agent is told to make it in smaller edits |
| File links fail                    | Check that this browser is signed in (a file by path opens only with the session's proof key or the file capability `k` the page asks for, so a link copied out of the page stops working after 10 minutes) and that the path is inside the allowed workspace or drive roots. The relay's secrets file, database and config are never served (403 `FILE_PROTECTED`); a wrong or expired `k` gets 403 `AUTH_FILE_CAPABILITY` |
| Claude missing from New Chat       | Enable it in **⚙️ Settings → Providers → Claude**; the toggle is off by default   |
| Claude reply says it cannot authenticate | Press **Claude settings** on the failed reply, then **Relogin** (or run `claude` on the relay host), and retry the turn |
| Claude Cloud missing from New Chat | Enable it in **⚙️ Settings → Providers → Claude Cloud**; it is off by default and needs a Claude login on the relay host |
| Claude Cloud reply says GitHub is not connected, or the Claude GitHub app has no access | Connect GitHub to the Claude account at [claude.ai/connect-github](https://claude.ai/connect-github), or add the repository to the Claude GitHub app's repository access on GitHub; then send the message again |
| New Chat says *No cloud environment is set* | Choose one in **⚙️ Settings → Providers → Claude Cloud**; an account without any gets its default one when you open claude.ai/code once |
| Grok reply says the CLI was not found | Press **Install Grok CLI** on the failed reply, or install it from **⚙️ Settings → Providers → Grok**; no relay restart is needed afterwards |
| Grok reply says authentication failed | Press **Sign in to Grok** on the failed reply and confirm the device code in a browser |
| DeepSeek reply says the balance is used up (`relay.deepseek-balance`) | Press **Top up DeepSeek** on the failed reply, top up on platform.deepseek.com, then send the message again |
| DeepSeek reply says the key was not accepted (`relay.deepseek-api-key`) | Press **DeepSeek settings** on the failed reply and paste a valid key |
| Claude API missing from New Chat, or the **Billing** field (`Subscription \| API key`) in the chat's **⚙** settings refuses the key | Switch it on in **⚙️ Settings → Providers → Claude API** with a saved key, and check that the month's spend has not reached the cap there (see [Claude API](providers.md#claude-api)) |
| **⚙️ Settings → Providers → Claude API** says *API key saved, but Anthropic refused it* with a 400, or every Claude API turn fails with HTTP 400 from Anthropic | A key that is not tied to a workspace gets HTTP 400. For now, create the key inside a workspace in the Claude Console and save that one; support for naming the workspace is planned |
| A Claude API reply says the key was not accepted, the credit balance is too low, or a spend limit is reached | Press **Claude API settings**, **Add funds**, **Console billing** or **Console limits** on the failed reply, fix it in the Claude Console, then send the message again |
| The Claude API card in **Check Usage** shows *no price known* for a model | Claude Code has no price for that model yet (currently Claude Haiku 5.5), so its tokens are listed but left out of the estimate; a month that also has priced models reads *(estimate incomplete)* |
| An image chat says *Daily image cap reached*, or an image reply or an agent's send fails with `OPENAI_IMAGE_DAILY_CAP_REACHED` | Today's OpenAI image spend has reached the relay's daily cap (USD 5 unless you changed it). Press **OpenAI image cap** on the failed reply, or open **⚙️ Settings → Providers → OpenAI**: raise **Daily image cap (USD)**, or press **Allow for today**; the cap starts over at midnight, relay time (see [OpenAI Image](providers.md#openai-byok-and-openai-image)) |
| An image reply ends with *the request may have been billed; retry the message* | OpenAI did not answer in time, answered with a server error, or the connection broke (or the relay restarted during the call); the relay tries at most twice and never a third time. Retry only if the cost is fine. A slow endpoint can get more time with `openaiImageGenerateTimeoutMs` and `openaiImageEditTimeoutMs` in [config.json](configuration.md#configuration-reference-serverconfigjson), up to 5 minutes |
| New messages stay queued and a banner says *Relay restart queued — waiting for N sessions* | A restart is queued and waits for the running turns of the sessions it links; until then no message is handed to a session. Wait, or press **Restart now** or **Cancel restart** in the banner. After **Ask after a queued relay restart has waited** (Settings › Relays, 30 min by default) the banner asks instead of waiting on |
| Long turn requeued unexpectedly    | Raise or clear **Max turn duration** in Settings (0 = no limit)                  |
| Background agent or shell stopped on its own | It reached the **Background task timeout** (default 4 h); raise it or set 0 for no limit |
| A task row says *no output for N min* in amber | The command has written nothing for longer than **Mark a background task as quiet after** (default 10 min). Open its console to see the last lines; a long, silent step is normal for some commands, so raise the setting, or **Stop** the task if it hangs |
| A task's console stops at *Output stops here: this command pipes into tail* | A command piped into `tail` writes nothing until it ends; the output arrives then. To follow such a run live, have it log to a file instead (`> run.log 2>&1`) and follow that file |
| After a relay restart a task's console says its output is *no longer available* | The relay keeps the console rows across a restart, from the first restart into a build that has them on. Until its worker reports, a running command's console says it is waiting for the worker; a command whose worker did not come back reads as finished with an unknown result. A command started before that build has no stored row and is back once its worker reports (a few seconds) |
| After a relay restart a session stopped mid-turn and did nothing more | Its turn could not run again (the agent had already taken the message). Send a short "carry on", or switch on **Settings → Relays → After a relay restart, tell interrupted sessions to carry on** so the relay does that itself next time. A row that says the relay restarted is that note; it is sent once per restart |
| After `oar restart` or `oar stop`, running turns and background tasks are gone | `--now`, or a relay that did not answer, went through `systemctl --user` at once, which ends running turns. Without `--now` both wait for running turns, under the service too. Session workers started by a relay of 0.9.20 or later run outside the service and keep running; a worker on a tmux server or in a process started before 0.9.20, inside the service, stops at its first full restart, once (see [Start the relay](install.md#start-the-relay)) |
| Formulas show as written (`$x^2$`), or **🖥️ Inspect tmux console** shows plain text without colours | The browser could not load KaTeX or xterm.js from jsDelivr (for the xterm.js scripts the console also tries unpkg; its stylesheet comes from jsDelivr only): it is offline, or a firewall, proxy or content blocker stops those addresses. The relay host's own access does not matter. A single formula shown as written while others render could not be parsed (see [Formulas in replies](web-ui.md#formulas-in-replies)) |
| A conversation will not delete     | It is still working: a running turn, one waiting on a question card or approval, or live background tasks. Stop it, then delete |
| Archive or delete says *Couldn't stop this conversation's session, so it was not archived* (or *… so nothing was deleted*) | A process of the conversation's worker still ran after the relay had stopped it, so nothing was changed. On Linux and macOS that is a process whose command line names the session, also one of another user, which the relay may not stop. Try again in a moment; if it keeps failing, end that process yourself. A worker that has already ended does not block it, also when its process id now belongs to another program |
| A reply says *The working directory of this conversation no longer exists*, or a worker launch note says *worker-spawn-failed: The working directory of this conversation no longer exists: …* (or *… is not a folder*) | The folder the conversation runs in was deleted, renamed or unmounted. Restore it, or choose another one with **🗂️ Change CWD** in the **︙** menu, then send the message again |
| A conversation seems wedged        | **☠️ Kill session** in the **︙** menu stops its worker; retry the turn or send a new message |
| An agent, a script or a tool gets 403 `AUTH_PERSON_REQUIRED` (*Only the person signed in to this relay can do this* or *Only the person can answer questions; ask them in the relay UI*) | It called with an agent token (`OAR_AGENT_TOKEN`, or `oar agent-token`'s), and the route is the person's: answering or dismissing a question card, settling a plan card, the Inbox, settings, pairings, push devices, shares, deleting a session, making or renaming groups, a restart now or a plain shutdown. Do it yourself in the relay UI. An agent may queue a restart (`{ "restart": true, "reason": "…" }`) and move a session into an existing group (see [Security notes](security.md)) |
| A script that called the relay's local API gets 401 *The relay token is no longer in the config; use OAR_AGENT_TOKEN* | The config holds no token any more. Send `Authorization: Bearer $OAR_AGENT_TOKEN` (set in every session's environment); outside a session, take the token `oar agent-token` prints |
| An action in the browser fails with 403 `AUTH_CROSS_SITE` | The request came from another page than the relay's own: a page on another port of the same host (an agent's preview, say), or another host of the same domain, counts as another site, even though the browser sends it the session cookie. Open the relay's own address. Behind a proxy that serves the relay under another origin, list that origin in `allowedOrigins` |
| The sign-in page says *This browser was signed out* (or a notification answer says *Signed out, open OAR*) | This browser's session no longer counts: it was signed out in Settings → Security (from this or another browser, or with "Sign out all other browsers"), it went unused for 30 days, it reached its 400 days, or more than 50 browsers signed in and it was the one used least recently. Sign in again with the relay token, or with a sign-in link from Settings → Security → Sign in another device. Signing out does not change the token |
| The sign-in page opens, or an action fails, with 403 `AUTH_SESSION_PROOF` | The request had the session cookie without the session's proof key. In the relay's own page that means this browser's key is gone (its site data was cleared): sign in again. From a page on another port of the relay host (an agent's preview or dev server) or a script that copied the cookie, it is the protection working: the cookie alone is not enough. Scripts use `OAR_AGENT_TOKEN` instead (see [Security notes](security.md)) |
| A call gets 403 `AUTH_COOKIE_UPGRADE` | The browser's cookie is from before sessions (it holds the relay token). The relay's page trades it for a session by itself, without the sign-in page; a tab left open from before the update runs the old page and needs one reload. A script that sends such a cookie gets this answer every time: give it `OAR_AGENT_TOKEN` |
| Signing in or starting the page gets 409 `AUTH_UPGRADE_PENDING` | Another tab of the same browser traded the old cookie for a session a moment ago; the page waits for that tab's key and goes on by itself. If it stays stuck, reload once after 10 seconds |
| A tab left open from before the update shows errors, signs out or does not update live | It still runs the earlier page, which does not send the session's proof key. Reload it once |
| After a new relay token, a script, a paired relay or a browser left open from an earlier version gets 401 | The old token stops working at once when a new one is made (Settings → Security, or `oar setup --new-token`). Browsers signed in with a session stay signed in; agents and `OAR_AGENT_TOKEN` keep working. A script that sent the token itself needs the new one (or `OAR_AGENT_TOKEN` on the relay host). Paired relays that sign in with a key of their own keep working; one that still calls with the token (an OAR before 0.9.27, or one without a key yet, the ones the new token's dialog lists) needs re-pairing: paste the new pairing link there (Settings → Relays → Add a relay); the existing entry is updated in place. The token is shown once; if you lost it, make another |
| `oar stop`, `oar stop --now`, `oar restart --now` or `oar uninstall` says *The relay refused: … is for you to do in the web UI* | The relay runs an earlier version, which takes only a queued restart from the `oar` command's agent token, or the call did not come straight over loopback (a proxy or tunnel in between). Stop the relay, or restart it at once, from the web UI (︙ → Restart web relay); under the systemd service `oar stop` and `--now` go through systemd. A plain `oar restart` waits for running turns and works |
| `oar stop --now`, `oar restart --now` or `oar uninstall` asks *…? [y/N]*, or says *No terminal to ask on. To go ahead without the question, run: … --yes* | On a terminal these ask first, because they cut running turns off (or remove OAR). Answer `y`. Without a terminal (a script, an agent's shell) they are refused unless you add `--yes` |
| An agent's `POST /api/relay/shutdown` gets 403 *An agent token gets the queued restart only* | A session's agent token may queue a restart and nothing else: send `{ "restart": true, "reason": "…" }`. A restart now or a stop is the person's, in the relay UI. The `oar` command's own token gets the same answer (*only straight over loopback*) when its call passes a proxy: a request with `X-Forwarded-For`, `Forwarded`, `X-Real-IP` or `X-Forwarded-Proto` is not loopback |
| A paired relay's answer, or this relay's log, says `REMOTE_RELAY_ORIGIN_MISMATCH` | A paired relay signed in with its own key and claimed to be another relay. It was refused and counted (Settings → Relays: "N refused claims since start"; the first one also puts a notice in the Inbox). An honest OAR never does this: check what runs on that relay, and **Revoke key** on its row if in doubt |
| `REMOTE_RELAY_PEER_KEY_REQUIRED` | On the relay that refused: a request claimed to be a paired relay that signs in with a key of its own, without that key; it was refused and counted on that relay. The same code answers an ask, a session watch or an Inbox read from a relay without a confirmed key. On the relay that was refused (its agent gets *Relay "…" refused this call … Ask the person to re-add relay "…" from its link*, and its row in Settings → Relays says **Re-add from link**): it holds no key the other relay takes (a restored backup, the key revoked or the entry removed there). Re-add that relay from its link: Settings → Relays → Add a relay, paste its pairing link; the existing entry is updated in place and keys follow both ways, also after a **Revoke key** there (the add renews the revoked key). Or, on the other relay, **Renew key** on this relay's row sends it a new key. A row that says **One way** and holds no key was added with **Also add this relay there** off to a relay older than 0.9.27: that relay lists no entry for this one, so it gives it no key and refuses its asks, watches and Inbox reads by design (prompts still go through, as claimed). Update it, then use **Re-pair** on that row to add this relay there. With 0.9.27 or later a one-way add gets a key of its own (inbound only there), so none of this applies |
| A paired relay's row in Settings → Relays says *Rejected the key it gave this relay (401)* | That relay no longer takes the key it gave this one: it was revoked there, or that relay removed its entry for this one. This relay asks it for a new key once; when that fails too the row says **Re-add from link**: paste that relay's pairing link (Settings → Relays → Add a relay) and the entry is updated in place. For a **One way** row this means the other relay removed this one from its **Inbound only** rows (or it was added there one way again from elsewhere): add it again from its link. *Rejected the token (401)* is a token instead: the one held for an unkeyed pairing (or a one-way pairing with a relay older than 0.9.27), replaced on that relay since |
| Adding a relay one way says *… could not be checked at its address …* or *… did not give this relay a key …*, and *Nothing was saved here* | The other relay was asked for an inbound-only key and the request or the check of the key failed (it went offline halfway, a proxy in front of it answered, or it refused the token from the link). Nothing was stored on this relay and its token was not kept; an unchecked key there opens nothing and lapses after 10 minutes. Press **Add** again. Settings → Relays on the other relay may show this relay as **Inbound only** meanwhile; adding again replaces its key |
| `REMOTE_RELAY_PEER_SCOPE` | A paired relay's key was used on a route outside the relay routes (settings, files, pairing, a session's billing, answering a card or an ask). That is by design; do it on the relay itself |
| A prompt from a paired relay shows **claimed**, its header line says "(unverified)", or the sending agent got *Arrived unverified: …* | That relay holds no confirmed key here (an OAR before 0.9.27, a one-way pairing, or a key not confirmed yet), so its claim to be that relay could not be checked. The prompt is kept but opens nothing (no reply access, no hop allowance). Update both relays to 0.9.27 or later and use **Re-pair** in Settings → Relays (Old version, Legacy token rows); an older relay's Re-pair opens the pairing-link field |
| I have no signed-in browser and lost the token (or never saw one: the relay was set up without a terminal) | To sign one browser in without the token, run `oar url --sign-in` in a terminal on the relay host while the relay runs: it prints a single-use link and its QR code for 10 minutes. To make a new token instead, run `oar setup --new-token` in a terminal on the relay host, type NEW: it shows a new token once, with a sign-in link, and restarts the relay. This rotates the token: browsers that are still signed in stay signed in, agents carry on, paired relays that sign in with their own key keep working; a paired relay of an older version (protocol 1) needs the new pairing link. A relay's first start without a terminal never prints its token, on purpose (see [Security notes](security.md#no-terminal-no-browser)) |
| `oar url` prints no `?token=` link | The relay keeps only a hash of its token, so no file holds one to print. Run `oar url --sign-in` in a terminal for a single-use sign-in link (and its QR code), or sign in with the token from your password manager; lost it? `oar setup --new-token` makes a new one and shows it once |
| `oar url --sign-in` prints no link | It says why. *only in a terminal*: it needs a terminal on stdin and stdout, and `--yes` does not stand in for one (in a script or an agent's shell use Settings → Security → Sign in another device). *OAR_AGENT_TOKEN is set*: you are in an agent's shell; use a terminal of your own. *The relay is not running*: `oar start`. *runs with its earlier settings*: `oar restart`, then ask again. *at most 3 sign-in links in 10 minutes*: wait the minutes it names. *does not make sign-in links for the oar command*: the relay is older, or the call passed a proxy (a request with `X-Forwarded-For`, `Forwarded`, `X-Real-IP` or `X-Forwarded-Proto` is not loopback); use Settings → Security → Sign in another device. A link stops working once a newer one is made |
| Sign-in says *Too many failed sign-in attempts* | Ten wrong tokens from one address within a minute lock that address out until the minute is over (see [Security notes](security.md)); wait, then use the right token. Behind a reverse proxy on another host, set `trustProxy`, or every visitor shares the proxy's address and its lockout (see [Behind a reverse proxy](remote-access.md#behind-a-reverse-proxy)) |
| Behind a reverse proxy the page loads but nothing updates live, and the log says `Refused a handshake from origin` | The proxy rewrites the `Host` header: list the public origin in `allowedOrigins`, or have the proxy pass `Host` on (see [Behind a reverse proxy](remote-access.md#behind-a-reverse-proxy)) |
| A shared link answers 404 | Its sharing was stopped or the link was renewed; **Settings → Sharing** lists the links that work |
| `npm install -g @oar-sh/oar` fails with `EACCES` | npm's global folder needs root (a distribution or NodeSource Node.js). Do not use `sudo`; run the installer (`curl -fsSL oar.sh/install \| sh`), which installs into `~/.oar/npm` instead |
| A chat shows *⏳ Installing the Claude Agent SDK on the relay host* (or the Cursor SDK) for a long time | The relay downloads the SDK once per version, before the chat's first turn: about 370 MB for Claude, 40–50 MB for Cursor. The chat stays usable meanwhile; your message waits in the queue and is delivered when the install ends. The SDK's row in **⚙️ Settings → Providers** (Claude, Claude API, DeepSeek or Cursor tab) shows the install log. *Installing by another OAR process* means another relay, or `oar sdk install`, on the same SDK folder is at it, and this relay waits for it. If the install fails, the chat shows the cause and the message stays queued; the rows below say what to do (see [Agent SDKs](install.md#agent-sdks)) |
| The install log in **⚙️ Settings → Providers** grows slowly on a slow link | Nothing to do while it moves: progress (npm's output, the bytes it downloads) is checked every 15 seconds, and only 5 minutes without any stops the install, as a network failure that is tried again after 1, 5 and 15 minutes. An install takes at most 2 hours, which needs about 0.4 Mbit/s for the Claude SDK. On a slower link, point npm at a registry mirror closer to the host (`npm config set registry …`, which the install uses), or run the install once while the link is faster; `oar sdk install` uses the same limits |
| An SDK row in **⚙️ Settings → Providers** (or **Windows helper** under General) says *Install failed* with *No connection to the npm registry* | The relay host could not reach the npm registry. The relay tries again by itself after 1, 5 and 15 minutes, and at its next start; press **Retry** once the host is online. OAR needs the registry once per SDK version and does not work offline; npm's registry, proxy and `cafile` settings apply |
| An SDK install failed with *The proxy asks for a login* (`E407`) | Put the proxy with its login into the npm config of the relay's user (`npm config set proxy …` and `https-proxy`), then press **Retry** |
| An SDK install failed with *The disk is full* (`ENOSPC`) | The Claude Agent SDK needs about 370 MB in the SDK folder, plus room in npm's cache. Free space, or move the folder to another disk with `OAR_SDK_DIR` and restart the relay, then press **Retry** |
| An SDK install failed with *npm's cache holds a damaged copy* (`EINTEGRITY`) | Run `npm cache verify` as the relay's user on the relay host, then press **Retry** |
| An SDK install failed with *npm installed … without …; check the npm config for omit, os or cpu settings* | Your npm config leaves out the vendor's platform package, which holds the SDK's binary: `omit=optional`, or an `os` or `cpu` setting for another platform. Check with `npm config get omit`, `npm config get os` and `npm config get cpu`, remove the setting from your `.npmrc`, then press **Retry** |
| An SDK row says *The SDK folder … is a network path* or *… is longer than 120 characters* | Both limits apply on Windows only. Set `OAR_SDK_DIR` in the relay's environment to a short folder on a local disk and restart the relay |
| An SDK row says *Not available on this platform*, or a chat's note says *… is not available on this platform* | The vendor publishes no build for the relay host's platform, so it is not retried (see the platform table in [Agent SDKs](install.md#agent-sdks)). The Cursor SDK has none for Windows on arm64; neither SDK has one for Android under Termux, 32-bit ARM or FreeBSD. On Android, run OAR inside a Debian under proot instead, which counts as Linux arm64 |
| A chat's note says *The worker for this conversation could not be started … could not be installed* | Its provider's SDK failed to install; the cause follows in the note. Fix it as in the rows above and press **Retry** in the SDK's row. The message stays queued: when that **Retry**, or the relay's automatic retry, installs the SDK, the message is delivered |
| **Reinstall** on Windows says *The folder … is in use; stop the sessions that use it, then try again* | Running Claude or Cursor sessions hold files of the installed SDK open, and Windows cannot move the folder while they do. The relay tries for about 30 seconds. Wait until those sessions are idle, or stop them with **☠️ Kill session**, then press **Reinstall** again |
| The Cloudflare tunnel stays off and the status dot's tooltip says `cloudflared is not installed` | OAR runs the `cloudflared` on the relay host and ships none. Install it (see [Cloudflare Tunnel](remote-access.md#optional-remote-internet-access-cloudflare-tunnel)); the tunnel starts within a minute |
| The relay stops at start with *better-sqlite3 has no prebuilt SQLite binding for …* | Your platform (Termux, 32-bit ARM, FreeBSD) needs the binding built: run `oar build-native`, then start the relay again. It needs Python 3, make and a C++ compiler; on Termux run `pkg install python clang make` first |
| The relay stops at start with *The SQLite binding of better-sqlite3 for … is missing from the installed package* | The install is incomplete; reinstall with `npm install -g @oar-sh/oar` |
| No usage line under a reply        | Expected for OpenAI, Claude, Claude API, Claude Cloud, Cursor, Grok, and DeepSeek turns; only Copilot turns record plan usage |
| The relay stopped with *JavaScript heap out of memory* in its log | See [The relay ran out of memory](#the-relay-ran-out-of-memory) below |
| After a deploy, About says *Workers: N, M on an older build* | Normal for a while: the relay replaces those workers by itself once their sessions are idle and their CLI has ended, usually some 10 minutes after the last turn. See [Workers after a deploy](#workers-after-a-deploy) below |
| The relay does not start: *Both …copilot.db and …oar.db are there* (exit code 78) | The data folder holds both database names, usually after going back to a version before 0.9.20 without renaming `oar.db` back, and work was done there. The relay changed nothing. Keep the one to go on with: stop the relay, move the other's three files (`copilot.db`, `copilot.db-wal`, `copilot.db-shm`, or the same of `oar.db`) into a folder of your own, start again. A `copilot.db` with no work in it (only the settings a start writes) is set aside by itself, as `copilot.db.older-<time>` |
| The relay does not start: *…oar.db-wal is there without …oar.db* (exit code 78) | A database's `-wal` (or `-shm`) was left behind by a rename by hand, often after an unclean stop. A database renamed to `oar.db` later, or a new one, would take its pages in and lose the rows written since. Move the file into a folder of your own and start again. Before renaming a database by hand in either direction, make sure no `-wal` or `-shm` of the target name is there |
| The relay does not start: *…relay-secrets.json exists but cannot be read* (exit code 78) | The file that holds the relay token's hash is there, but the relay's user cannot read it (its owner or permissions changed, a folder in its place) or another program holds it open. The relay does not make a new token over it. Fix the file's owner and permissions (`chmod 600`, owned by the relay's user), or close what holds it, then `oar start`. The supervisor, the systemd service and the CLI extension do not retry exit code 78 |
| After going back to 0.9.26 or earlier, the relay answers 401 | That version reads its token from `config.json`, which no longer holds one (this version keeps only a hash), so it makes up a new one at each start. Run `oar setup --new-token` there, or go forward again. Going forward after that `--new-token`: the token it wrote into `config.json` becomes the relay token, the web UI shows *The relay token was changed outside OAR*, and the token you had made in the newer version before going back no longer works. Dismiss the notice if this was you, and replace the token once more if you like |
| After going back to 0.9.26 or earlier, paired relays show *unauthorized* | That version cannot use the keys paired relays sign in with since 0.9.27, and this version stored those pairings so that the older one sends a placeholder the other relay refuses, not its own relay token. Remove each paired relay in **⚙️ Settings → Relays** and pair it again. Do the removing before you go back: the older version sends its relay token, once a minute, to any pairing it reads as using that token (one edited by hand, or written by a build from before 0.9.27) |
| The log or About says *[backup] skipped* or *failed* | The relay went on without a copy of the version before: a full disk (it keeps max(1 GiB, 5 %) free), a backup folder with a `DO_NOT_TOUCH` file, or a relative `dbBackups.dir`. Fix the cause and run `oar backup`; the next new version tries again by itself |

## Restore a database backup

The relay's backups are in `backups/` of the state root (`server/backups/` in a git checkout, or `dbBackups.dir`); `oar doctor` lists them. Each is one file, `oar-<version>-<time>-<reason>.db` (the time in UTC), named after the version that ran on the data, the one to go back to. A first backup that could not tell (reason `pre-update-from-unknown`, after `oar update` to 0.9.20 or a `git pull`) carries the running version instead and holds the data of the version before it.

1. Stop the relay (`oar stop`, or the systemd service or autostart fully, so nothing starts it again).
2. Move the live database files out of the data folder into a folder of your own: `oar.db`, `oar.db-wal`, `oar.db-shm`, and `copilot.db`, `copilot.db-wal`, `copilot.db-shm` (whichever are there; `oar doctor` says which the relay runs on).
3. Copy the backup into the data folder under the name the version you start runs on: `copilot.db` for a version before 0.9.20; for 0.9.20 and later the name the relay ran on (`oar.db` unless it still ran on `copilot.db`). It is one file: no `-wal` or `-shm` belongs to it.
4. Start that version (`oar update --to <version>`, or that commit in a checkout).

A restored database also holds an older record of the relay token's hash. When the token was replaced with `oar setup --new-token`, or changed outside OAR, after that backup was made, the next start shows *The relay token was changed outside OAR*: expected after a restore you did yourself, so dismiss it (a replacement in the web UI after the backup raises none). The token in force is the one in `relay-secrets.json`, whatever the database says.

The restored database names the old version as the last one that ran on it, so a later start of a newer version backs it up again before its migrations. Open a backup only read-only (`sqlite3 'file:<backup>?immutable=1'`): opening it to write makes `-wal` and `-shm` files beside it and can change it.

## Workers after a deploy

A session worker loads its code when it starts. A relay restart after a deploy or an update gives the relay new code, but the workers only reconnect and would keep running the old one. So every worker states the build it started on (version and commit), and the relay replaces a worker on another build, or one too old to state any, the way **🗂️ Change CWD** relaunches it: it stops the worker and starts a new one on the same conversation.

The relay replaces a worker only when two things hold: the session is idle (no running turn, open question card, compaction, background task, or message on its way in), and the worker's CLI has ended. A CLI that has gone quiet ends by itself about 10 minutes after the last delivery or turn; until then a job it scheduled may still wake it, so the relay leaves it alone. A worker that reports whether its CLI runs is replaced once it says the CLI is gone. One too old to report that is replaced only after 10 minutes without a delivery or a turn end, the same window. So a session is usually replaced some 10 minutes after its last turn, not right after the deploy. The relay starts at most two at a time, one every 3 seconds. The worker of an archived conversation is stopped and not started again. Nothing needs to be done by hand.

What a replacement can and cannot lose:

- **The conversation:** nothing. The new worker resumes the native session from its transcript.
- **A message:** nothing. A message sent during the replacement waits and goes to the new worker.
- **Background tasks:** none, for the Claude, Copilot, Grok and Claude Cloud workers: a session with one running is not idle, so its worker is not replaced. The Cursor worker is the exception: its SDK does not tell the worker about background shells or background tasks, so for a Cursor session only the 10-minute quiet window protects them.
- **Jobs scheduled inside the CLI** (`CronCreate`, `ScheduleWakeup`): they last exactly as long as they would without a replacement. They live in the CLI, and the relay waits for the CLI's own idle-out, which ends them in any case.
- **What it costs:** one cold start on the session's next message.

To see where it stands:

- **About OAR** shows *Workers: 14, all on this build* or *Workers: 14, 3 on an older build* under the version.
- `/api/status` gives the relay's own build in `sessionWorker.buildId`, and `buildId`, `startedAt` and `stale` for each entry of `sessionWorker.workers`. `sessionWorker.recycle` has `staleCount`, the replacements in flight and done, and in `waiting` the sessions that are held, with the reason.
- The relay's log has a `[worker-recycle] recycling <session>` line before each replacement and a `recycled <session> pid <old>→<new>` line after it, and at most once a minute per session a `waiting <session>: <reason>` line while one is held. The reason is `turn`, `question`, `compaction` or `background` for a busy session, `cli` for an idle one whose CLI still runs, and `quiet` for an idle worker too old to report its CLI, inside its 10 minutes.

`waiting <session>: cli` or `: quiet` for up to about 10 minutes after a session's last turn is the normal case. A `staleCount` (or *M on an older build*) that stays above zero for much longer means a session that never goes idle (a background task that runs for hours, a question card nobody answers, a scheduled job that keeps waking the CLI); finish or stop that, or use **☠️ Kill session**. A `still on <build> after a recycle` warning means the replacement came up on the old build again: the workers start from another code tree than the relay's (another `COPILOT_WEB_RELAY_ROOT`, or a `package.json` one side cannot read), and the relay does not try that session again under this build.

A chat note that the relay *could not stop this chat's old worker* means a stop that failed three times: see [A chat's old worker does not stop](#a-chats-old-worker-does-not-stop).

## A chat's old worker does not stop

**Symptom:** a chat shows the note *⚠️ The relay could not stop this chat's old worker (pid …) to restart it on the updated code*, and the relay's log has `[worker-recycle] session <session> is stuck: 3 recycle attempts failed (last: stop: …)`, after `STOP FAILED session=<session> … remaining=<pid>` lines from `WORKER RECYCLE`. The usual reason in the note is `worker-not-in-process-list` (the worker's process still runs, but the process list the relay reads does not show it as that session's worker, so the stop never reached it) or `worker-survived-stop` (it outlived the stop). The note names a pid only when the relay checked that the process is still that chat's worker (its command line names the session, it started when the worker did); a note without a pid means the relay could not tell what runs under the old pid.

The relay retries the stop every minute at most, but until it goes through, the old worker may go on serving the chat on the old code, and a message can fail if the update removed the files that worker runs from (an agent SDK's old folder, for example). After an update, such a worker's messages wait for the first three tries: about 15 seconds of backoff between them plus the time the three stops take. After that the old worker gets them again.

**Way out:** stop the old worker by hand. The next try then finds it gone and starts a new worker on the current code, within a minute.

- The note and the `remaining=` part of the log line give its pid. On Linux and macOS, `kill <pid>`, and `kill -9 <pid>` if it is still there after a few seconds; on Windows, `taskkill /PID <pid> /T /F`.
- Without the pid, look for the session id in the command lines: every worker runs as `node <kind>-session-worker.mjs --session-id <session id>`. On Linux and macOS, `ps -eo pid,args | grep -- '--session-id <session id>'`; on Windows, in PowerShell, `Get-CimInstance Win32_Process | Where-Object CommandLine -like '*<session id>*' | Select-Object ProcessId, CommandLine`. `/api/status` lists every worker with its `sdkSessionId` and `pid` in `sessionWorker.workers`.
- Check the process before you stop it: its command line must carry the chat's `--session-id`. A pid is handed out again once its process ends, so a pid that runs something else is no longer the worker; leave it alone.

Restarting the relay (**🌄 Restart web relay**, `oar restart`) does not end the worker, since workers keep running through a restart; it only starts the tries over, which helps when the cause was passing (a process list that could not be read for a moment).

## The relay ran out of memory

The relay runtime starts with a fixed heap limit. By default it is 60 % of the host's RAM, in 64 MB steps, with a minimum of 2048 MB and a maximum of 8192 MB, and never below Node's own default. On a 4 GB host that is about 2.3 GB. Every start logs the limit and where it came from, such as `[relay] heap limit 2368 MB (default: 60% of 3.9 GB RAM)`. Every 10 minutes the status log gets a line such as `[relay] memory rss=812 heapUsed=640 heapLimit=2560`. One extra `[relay] memory high: …` line is logged when the used heap passes 80 % of the limit.

To set the limit yourself, put `heapLimitMb` (whole MB, at least 512) in `config.json` and restart the relay. Every launcher reads it: `oar start`, the systemd service, Windows autostart and the CLI extension. A `--max-old-space-size` in `NODE_OPTIONS`, or on the `node` command line that starts `server.js`, wins over `heapLimitMb` and is not added twice. Unlike `heapLimitMb`, `NODE_OPTIONS` set in a shell is lost when something else relaunches the relay.

When the heap nears its limit, Node writes one heap snapshot (`Heap.<date>.<pid>.….heapsnapshot`) to the `diagnostics` folder in the relay's data directory: `~/.oar/data/diagnostics`, `%APPDATA%\oar\data\diagnostics` on Windows, or `server/data/diagnostics` in a checkout. The relay creates that folder and logs its path at start. On Linux and macOS it makes the folder owner-only (0700); on Windows the folder keeps the permissions of the data folder it sits in. A `--diagnostic-dir` you set yourself is used as it is.

- **Disk:** a snapshot is about as large as the heap in use, so up to the heap limit. The data directory also holds the database, so when its drive has less than twice the heap limit free, the relay starts without a snapshot and logs why.
- **Memory:** Node can need up to about twice the heap in use to write the snapshot, and the relay stops responding while it writes. On a small host, writing it can fail or get the process killed. In that case the relay ends as it would have without the snapshot.
- **What to do with one:** copy it off the host, open it in Chrome DevTools (**Memory** tab → **Load**), and sort by *Retained size* to see what holds the memory. Comparing it with a snapshot from an earlier, healthy run shows what grew. A snapshot holds everything that was in memory, including the auth token and provider API keys, so never share one as it is. Delete it once it has been read: the relay never deletes snapshots, and the start line counts how many are there.

After a runtime crashes, including one that ran out of memory, the relay's own supervisor relaunches it up to 2 times; the 3rd crash in a row stops the relay with exit code 1. A run of 10 minutes or more resets the count. Under the systemd service, `Restart=on-failure` then starts a fresh supervisor after 2 seconds; a relay that keeps failing is started with longer and longer waits, up to every 5 minutes, and never given up (systemd before 254: every 10 seconds). `systemctl --user status oar` shows the state, `journalctl --user -u oar` why. A relay that stopped on purpose (exit code 78, a database or data folder that needs a decision) is not started again: fix the cause, then `oar start`.
