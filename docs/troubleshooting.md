# Troubleshooting

Symptoms and what to check. This is the detail behind the [README](../README.md#troubleshooting); the most complete guide is [Troubleshooting on oar.sh](https://oar.sh/docs/troubleshooting/).

| Symptom                            | What to check                                                                    |
| ---------------------------------- | -------------------------------------------------------------------------------- |
| Banner says *CLI is offline*       | No session worker has reported in during the last 10 seconds, which can be normal on an idle relay. Send a message: the relay starts that conversation's worker, and the banner clears once it connects. If it stays, check `/api/status` and the worker's `worker-<session>.log` in the log directory |
| `oar copilot` says the GitHub CLI is missing | It runs `gh copilot` beside the relay. Install the GitHub CLI, or [run only the relay](install.md#start-the-relay) |
| WSL: the browser on Windows shows another relay, or refuses the token | In WSL's default networking a port can be free in the distro while a Windows program listens on it; `localhost:<port>` in a Windows browser then reaches that program. `oar setup` picks a port that is free on both sides, and `oar status`, `oar start` and `oar doctor` warn when Windows holds the relay's port: choose another with `oar setup --port <port>` |
| Settings refuses the **SDK** engine | Install or upgrade the Copilot CLI, run `copilot` once, and restart the relay (see [engine choice](providers.md#github-copilot--engine-choice)) |
| Messages stuck pending             | Only one relay may run per data directory (a second one exits on the singleton lock), and only one process may own port `3333`. `oar doctor` shows the config and database in use |
| Messages to one conversation stay queued after a relay restart | Its worker reconnects by itself, retrying every 8 seconds at most. Its `worker-<session>.log` shows a `worker ws disconnected <reason>` line per failed attempt (the first three, then one a minute), which says why it cannot connect. **☠️ Kill session** in the `⋯` menu starts a new worker |
| Wrong or old model list            | **🤗 Select Models → Refresh** reruns discovery; `/api/model-variants` shows the Copilot catalog's `source` and `refreshedAt` |
| A send says *This conversation's model … is no longer available* | The model the conversation was set to has left the Copilot catalog, and the send named no model of its own. Pick a model in the composer and send again; the relay no longer switches such a conversation to another model by itself |
| Clarification card not progressing | Answer via the web card; the turn resumes once the question status becomes `answered` |
| File links fail                    | Verify auth token/cookie and that paths are inside allowed workspace/drive roots |
| Claude missing from New Chat       | Enable it in **⚙️ Settings → Providers → Claude**; the toggle is off by default   |
| Claude reply says it cannot authenticate | Press **Claude settings** on the failed reply, then **Relogin** (or run `claude` on the relay host), and retry the turn |
| Claude Cloud missing from New Chat | Enable it in **⚙️ Settings → Providers → Claude Cloud**; it is off by default and needs a Claude login on the relay host |
| Claude Cloud reply says GitHub is not connected, or the Claude GitHub app has no access | Connect GitHub to the Claude account at [claude.ai/connect-github](https://claude.ai/connect-github), or add the repository to the Claude GitHub app's repository access on GitHub; then send the message again |
| New Chat says *No cloud environment is set* | Choose one in **⚙️ Settings → Providers → Claude Cloud**; an account without any gets its default one when you open claude.ai/code once |
| Grok reply says the CLI was not found | Press **Install Grok CLI** on the failed reply, or install it from **⚙️ Settings → Providers → Grok**; no relay restart is needed afterwards |
| Grok reply says authentication failed | Press **Sign in to Grok** on the failed reply and confirm the device code in a browser |
| DeepSeek reply says the balance is used up (`relay.deepseek-balance`) | Press **Top up DeepSeek** on the failed reply, top up on platform.deepseek.com, then send the message again |
| DeepSeek reply says the key was not accepted (`relay.deepseek-api-key`) | Press **DeepSeek settings** on the failed reply and paste a valid key |
| Claude API missing from New Chat, or the chat's `Subscription \| API key` toggle refuses the key | Switch it on in **⚙️ Settings → Providers → Claude API** with a saved key, and check that the month's spend has not reached the cap there (see [Claude API](providers.md#claude-api)) |
| **⚙️ Settings → Providers → Claude API** says *API key saved, but Anthropic refused it* with a 400, or every Claude API turn fails with HTTP 400 from Anthropic | A key that is not tied to a workspace gets HTTP 400. For now, create the key inside a workspace in the Claude Console and save that one; support for naming the workspace is planned |
| A Claude API reply says the key was not accepted, the credit balance is too low, or a spend limit is reached | Press **Claude API settings**, **Add funds**, **Console billing** or **Console limits** on the failed reply, fix it in the Claude Console, then send the message again |
| The Claude API card in **Check Usage** shows *no price known* for a model | Claude Code has no price for that model yet (currently Claude Haiku 5.5), so its tokens are listed but left out of the estimate; a month that also has priced models reads *(estimate incomplete)* |
| New messages stay queued and a banner says *Relay restart queued — waiting for N sessions* | A restart is queued and waits for the running turns of the sessions it links; until then no message is handed to a session. Wait, or press **Restart now** or **Cancel restart** in the banner. After **Ask after a queued relay restart has waited** (Settings › General, 30 min by default) the banner asks instead of waiting on |
| Long turn requeued unexpectedly    | Raise or clear **Max turn duration** in Settings (0 = no limit)                  |
| Background agent or shell stopped on its own | It reached the **Background task timeout** (default 4 h); raise it or set 0 for no limit |
| A task row says *no output for N min* in amber | The command has written nothing for longer than **Mark a background task as quiet after** (default 10 min). Open its console to see the last lines; a long, silent step is normal for some commands, so raise the setting, or **Stop** the task if it hangs |
| A task's console stops at *Output stops here: this command pipes into tail* | A command piped into `tail` writes nothing until it ends; the output arrives then. To follow such a run live, have it log to a file instead (`> run.log 2>&1`) and follow that file |
| After a relay restart a task's console says its output is *no longer available* | The relay keeps the console rows across a restart, from the first restart into a build that has them on. Until its worker reports, a running command's console says it is waiting for the worker; a command whose worker did not come back reads as finished with an unknown result. A command started before that build has no stored row and is back once its worker reports (a few seconds) |
| After a relay restart a session stopped mid-turn and did nothing more | Its turn could not run again (the agent had already taken the message). Send a short "carry on", or switch on **Settings → General → After a relay restart, tell interrupted sessions to carry on** so the relay does that itself next time. A row that says the relay restarted is that note; it is sent once per restart |
| After `oar restart` or `oar stop`, running turns and background tasks are gone | `--now`, or a relay that did not answer, went through `systemctl --user` at once, which ends running turns. Without `--now` both wait for running turns, under the service too. Session workers started by a relay of 0.9.20 or later run outside the service and keep running; a worker on a tmux server or in a process started before 0.9.20, inside the service, stops at its first full restart, once (see [Start the relay](install.md#start-the-relay)) |
| A conversation will not delete     | It is still working: a running turn, one waiting on a question card or approval, or live background tasks. Stop it, then delete |
| A reply says *The working directory of this conversation no longer exists*, or a worker launch note says *worker-spawn-failed: The working directory of this conversation no longer exists: …* (or *… is not a folder*) | The folder the conversation runs in was deleted, renamed or unmounted. Restore it, or choose another one with **🗂️ Change CWD** in the `⋯` menu, then send the message again |
| A conversation seems wedged        | **☠️ Kill session** in the `⋯` menu stops its worker; retry the turn or send a new message |
| Sign-in says *Too many failed sign-in attempts* | Ten wrong tokens from one address within a minute lock that address out until the minute is over (see [Security notes](security.md)); wait, then use the right token. Behind a reverse proxy on another host, set `trustProxy`, or every visitor shares the proxy's address and its lockout (see [Behind a reverse proxy](remote-access.md#behind-a-reverse-proxy)) |
| Behind a reverse proxy the page loads but nothing updates live, and the log says `Refused a handshake from origin` | The proxy rewrites the `Host` header: list the public origin in `allowedOrigins`, or have the proxy pass `Host` on (see [Behind a reverse proxy](remote-access.md#behind-a-reverse-proxy)) |
| A shared link answers 404 | Its sharing was stopped or the link was renewed; **Settings → Sharing** lists the links that work |
| `npm install -g @oar-sh/oar` fails with `EACCES` | npm's global folder needs root (a distribution or NodeSource Node.js). Do not use `sudo`; run the installer (`curl -fsSL oar.sh/install \| sh`), which installs into `~/.oar/npm` instead |
| The relay does not start after an install with npm 12 (a `better-sqlite3` error in `server-err.log` in the log directory, or under the systemd service in `journalctl --user -u oar`) | npm 12 skipped the install scripts of OAR's native dependencies. Reinstall with `npm install -g --allow-scripts=@oar-sh/oar,better-sqlite3,koffi @oar-sh/oar` |
| The Cloudflare tunnel stays off and the status dot's tooltip says `cloudflared is not installed` | OAR runs the `cloudflared` on the relay host and ships none. Install it (see [Cloudflare Tunnel](remote-access.md#optional-remote-internet-access-cloudflare-tunnel)); the tunnel starts within a minute |
| `npm install -g @oar-sh/oar` fails with node-gyp or prebuild errors | `better-sqlite3` has no prebuilt binary for your platform; install a C/C++ build toolchain and Python, then retry |
| No usage line under a reply        | Expected for OpenAI, Claude, Claude API, Claude Cloud, Cursor, Grok, and DeepSeek turns; only Copilot turns record plan usage |
| The relay stopped with *JavaScript heap out of memory* in its log | See [The relay ran out of memory](#the-relay-ran-out-of-memory) below |
| The relay does not start: *Both …copilot.db and …oar.db are there* (exit code 78) | The data folder holds both database names, usually after going back to a version before 0.9.20 without renaming `oar.db` back, and work was done there. The relay changed nothing. Keep the one to go on with: stop the relay, move the other's three files (`copilot.db`, `copilot.db-wal`, `copilot.db-shm`, or the same of `oar.db`) into a folder of your own, start again. A `copilot.db` with no work in it (only the settings a start writes) is set aside by itself, as `copilot.db.older-<time>` |
| The relay does not start: *…oar.db-wal is there without …oar.db* (exit code 78) | A database's `-wal` (or `-shm`) was left behind by a rename by hand, often after an unclean stop. A database renamed to `oar.db` later, or a new one, would take its pages in and lose the rows written since. Move the file into a folder of your own and start again. Before renaming a database by hand in either direction, make sure no `-wal` or `-shm` of the target name is there |
| The log or About says *[backup] skipped* or *failed* | The relay went on without a copy of the version before: a full disk (it keeps max(1 GiB, 5 %) free), a backup folder with a `DO_NOT_TOUCH` file, or a relative `dbBackups.dir`. Fix the cause and run `oar backup`; the next new version tries again by itself |

## Restore a database backup

The relay's backups are in `backups/` of the state root (`server/backups/` in a git checkout, or `dbBackups.dir`); `oar doctor` lists them. Each is one file, `oar-<version>-<time>-<reason>.db` (the time in UTC), named after the version that ran on the data, the one to go back to. A first backup that could not tell (reason `pre-update-from-unknown`, after `oar update` to 0.9.20 or a `git pull`) carries the running version instead and holds the data of the version before it.

1. Stop the relay (`oar stop`, or the systemd service or autostart fully, so nothing starts it again).
2. Move the live database files out of the data folder into a folder of your own: `oar.db`, `oar.db-wal`, `oar.db-shm`, and `copilot.db`, `copilot.db-wal`, `copilot.db-shm` (whichever are there; `oar doctor` says which the relay runs on).
3. Copy the backup into the data folder under the name the version you start runs on: `copilot.db` for a version before 0.9.20; for 0.9.20 and later the name the relay ran on (`oar.db` unless it still ran on `copilot.db`). It is one file: no `-wal` or `-shm` belongs to it.
4. Start that version (`oar update --to <version>`, or that commit in a checkout).

The restored database names the old version as the last one that ran on it, so a later start of a newer version backs it up again before its migrations. Open a backup only read-only (`sqlite3 'file:<backup>?immutable=1'`): opening it to write makes `-wal` and `-shm` files beside it and can change it.

## The relay ran out of memory

The relay runtime starts with a fixed heap limit. By default it is 60 % of the host's RAM, in 64 MB steps, with a minimum of 2048 MB and a maximum of 8192 MB, and never below Node's own default. On a 4 GB host that is about 2.3 GB. Every start logs the limit and where it came from, such as `[relay] heap limit 2368 MB (default: 60% of 3.9 GB RAM)`. Every 10 minutes the status log gets a line such as `[relay] memory rss=812 heapUsed=640 heapLimit=2560`. One extra `[relay] memory high: …` line is logged when the used heap passes 80 % of the limit.

To set the limit yourself, put `heapLimitMb` (whole MB, at least 512) in `config.json` and restart the relay. Every launcher reads it: `oar start`, the systemd service, Windows autostart and the CLI extension. A `--max-old-space-size` in `NODE_OPTIONS`, or on the `node` command line that starts `server.js`, wins over `heapLimitMb` and is not added twice. Unlike `heapLimitMb`, `NODE_OPTIONS` set in a shell is lost when something else relaunches the relay.

When the heap nears its limit, Node writes one heap snapshot (`Heap.<date>.<pid>.….heapsnapshot`) to the `diagnostics` folder in the relay's data directory: `~/.oar/data/diagnostics`, `%APPDATA%\oar\data\diagnostics` on Windows, or `server/data/diagnostics` in a checkout. The relay creates that folder and logs its path at start. On Linux and macOS it makes the folder owner-only (0700); on Windows the folder keeps the permissions of the data folder it sits in. A `--diagnostic-dir` you set yourself is used as it is.

- **Disk:** a snapshot is about as large as the heap in use, so up to the heap limit. The data directory also holds the database, so when its drive has less than twice the heap limit free, the relay starts without a snapshot and logs why.
- **Memory:** Node can need up to about twice the heap in use to write the snapshot, and the relay stops responding while it writes. On a small host, writing it can fail or get the process killed. In that case the relay ends as it would have without the snapshot.
- **What to do with one:** copy it off the host, open it in Chrome DevTools (**Memory** tab → **Load**), and sort by *Retained size* to see what holds the memory. Comparing it with a snapshot from an earlier, healthy run shows what grew. A snapshot holds everything that was in memory, including the auth token and provider API keys, so never share one as it is. Delete it once it has been read: the relay never deletes snapshots, and the start line counts how many are there.

After a runtime crashes, including one that ran out of memory, the relay's own supervisor relaunches it up to 2 times; the 3rd crash in a row stops the relay with exit code 1. A run of 10 minutes or more resets the count. Under the systemd service, `Restart=on-failure` then starts a fresh supervisor after 2 seconds; a relay that keeps failing is started with longer and longer waits, up to every 5 minutes, and never given up (systemd before 254: every 10 seconds). `systemctl --user status oar` shows the state, `journalctl --user -u oar` why. A relay that stopped on purpose (exit code 78, a database or data folder that needs a decision) is not started again: fix the cause, then `oar start`.
