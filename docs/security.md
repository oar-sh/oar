# Security notes

What protects the relay, and what it deliberately does not. This is the detail behind the [README](../README.md#security-notes); the most complete guide is [Remote access security on oar.sh](https://oar.sh/docs/remote-access/security/).

- The relay token (the owner token) guards the API and the Socket.IO channel. It is the person's sign-in credential: keep it in your password manager. The relay stores only its SHA-256, in `relay-secrets.json` in its data folder (owner-only, written whole through a temp file), never the token itself: not in the config, the environment, the command line or the logs. `oar setup` on a terminal shows a new token once, with a sign-in link and QR code; `oar url` prints the address without a token (`oar url --sign-in` prints a single-use sign-in link instead, see below). Without a terminal nothing prints a token: a relay's first start, or `oar setup` run by a script, makes one and stores only its hash, because their output goes to a log file agents can read (see [No terminal, no browser](#no-terminal-no-browser)). A browser signs in once, with the token or with a URL carrying `?token=` (or a sign-in code, below), and then holds a browser session in its cookie, never the token itself. The `?token=` works on the page address only: the page takes it out of the address and exchanges it for a session; API, file and asset URLs accept the `Authorization` header or the cookie, not a `?token=`, and a Socket.IO handshake does not read a `token` query either.
- **Browser sessions.** Signing in (`POST /api/auth/session` with the token or a sign-in code) makes a session for that browser: its cookie `copilot_auth` holds a random `oars1_…` secret, and the relay keeps only that secret's SHA-256 (the `browser_sessions` table). The cookie is `HttpOnly`, `SameSite=Lax`, host-only (never a `Domain` attribute, so other hosts of the same domain do not get it), scoped to the relay's path, and `Secure` when the relay is reached over HTTPS, behind a TLS proxy the relay trusts through [`trustProxy`](configuration.md#configuration-reference-serverconfigjson) too; over plain http (LAN, localhost) it is not `Secure`, because a browser would drop a `Secure` cookie there. A session lasts 30 days from its last use and 400 days at most; the relay writes "last seen" and sends the cookie again at most every 10 minutes, and removes expired sessions at start and hourly. It keeps at most 50; a new one pushes out the one used least recently. A session can be signed out on its own: the relay then refuses its cookie at once (401 `AUTH_SIGNED_OUT`), drops its live connection, and removes that device's push subscriptions unless another of its sessions is still signed in. A session that is pushed out by the 50 or expires goes the same way.
- **The session's proof key.** Cookies are not isolated by port: a browser sends the relay's cookie to every port of the relay host (RFC 6265 §8.5), so a dev server an agent runs there receives it whenever you open that server, from the relay host or from a phone on your LAN, and could replay it. So the cookie alone is not enough. Signing in also gives the page a second secret, the session's proof key (`oark1_…`), once, in the sign-in answer and never in a cookie or a URL; the relay keeps only its SHA-256. The page keeps it in its own storage (localStorage, and IndexedDB for the service worker), which belongs to the relay's origin, port included, and sends it as `X-OAR-Session-Proof` with every API request, and as `auth.proof` in the Socket.IO handshake. A request with the cookie and without the right key gets 403 `AUTH_SESSION_PROOF`, reads included, and a handshake without it is refused. Requests with an `Authorization` header (the relay token, agent tokens, a paired relay's key) need no key. A browser whose key is gone (its site data cleared) is signed out: the relay never makes a key for a cookie alone, so that browser signs in again. The one exception that goes on the cookie alone is content the relay names by id or hash and a browser loads by itself, without a way to add a header (pictures, video, a download): `GET /api/upload/:sha256/content`, `GET /api/generated-image/…/content` and `…/partials/:fileName`, and `GET /api/media/:id/content`, which is tag-gated: media ids count up, so an id alone opens nothing, and every address the relay hands out for one carries a tag `t` (an HMAC of the id under a key derived from the agentKey); a missing or wrong tag gets 404 whoever asks, before the relay looks anything up. The tag never expires, so a browser may keep the picture, but when the agentKey changes (a new `relay-secrets.json`) old media addresses stop working and the gallery hands out new ones. Each of them serves file bytes, changes nothing, and is open to an agent token too (`COOKIE_ONLY_API_ROUTES` in `shared/relay-route-policy.mjs`; a test walks them). Settings → Security lists the browsers (label, created, last seen, last address) with Rename and Sign out, "Sign out all other browsers" and "Sign out this browser" (API: `GET /api/auth/sessions`, `PATCH` and `DELETE /api/auth/sessions/:id`, `DELETE /api/auth/sessions`, `DELETE /api/auth/session`).
- **File capabilities.** The two routes that read any file by its path, `GET /api/drives/file` and `GET /api/files/…`, are not on that list: with the cookie they need the proof key, or a file capability. The page loads files by path natively (a picture, a video with its range requests, a download, a PDF in a new tab) with a `k` parameter in the address, which it asks for with its proof key at `POST /api/files/capability` (`{ urls }` in, the same addresses with their `k` out; a browser session only: agents read files with their own token, paired relays are refused, the relay token gets the addresses back unchanged). A `k` is `fc1.<session id>.<expiry>.<HMAC>`: an HMAC-SHA256 under a key derived from the relay's `agentKey` (it never leaves the relay) over the browser session's id, the exact path the route is asked for (absolute and normalized, as text) and an expiry at most 10 minutes out. It opens that one file, range requests included, and only together with that session's own cookie, until it expires or the session is signed out or expires; another file, another session, an altered or an expired `k` gets 403 `AUTH_FILE_CAPABILITY`, the same answer whatever the path (missing, a link, one of the files below): the relay checks the `k` first, its form, expiry and session before the route runs and its HMAC before the route resolves a link, looks at the disk or lists the drives, and only then checks the real path like any other. The page asks for many at once, renews a link's `k` before it runs out, and asks once more when a load fails, so a long video goes on. A page on another port of the host that replays the cookie therefore reads no file by path.
- **Files no route serves.** Whatever the credential (the relay token, an agent token, a browser session, a file capability), the file and file-preview routes refuse the relay's own secrets (`relay-secrets.json`, `relay-previous.json`), its database (`oar.db` or `copilot.db` with their `-wal`, `-shm` and `-journal` files, and any database file, a backup being written (`*.db.partial`) included, in the data folder, the backup folder or the folders an upgrade takes an earlier database from; the secrets file's temporary copy during a write too) and its config file (`COPILOT_WEB_RELAY_CONFIG`, or `config.json`): 403 `FILE_PROTECTED`. These files, and any folder holding one (the data folder, the backup folder, the folder around them), cannot be read, changed, moved or deleted through OAR's file routes: the explorer's new folder, rename and delete refuse them for every credential, and the media gallery never serves one a message names. Paths are compared after resolving symlinks, and by file identity, so a link or a hard link to one of them is refused too. This keeps those files out of the file routes; an agent's own shell can still read them (see below).
- **Sign-in codes.** "Sign in another device" (Settings → Security, see [the web UI](web-ui.md#security)) makes a link `…/?signin=oarc1_…` that signs one browser in, once, within 10 minutes, without the token changing hands; the page shows it with a Copy button, and its QR code only after a tap on **Show QR code**; the code hides again after 60 seconds, when the page goes to the background or Settings closes, when a browser signs in with a sign-in link, when the link expires, and on **Hide QR code**. The relay keeps the code only as a hash, in memory (a restart ends it). Only the person can make one (`POST /api/auth/signin-codes`); a new one revokes the previous code of the same browser, and the answer carries the link's QR code as a module matrix, so no second request carries the code. A wrong or used code counts toward the lockout below like a wrong token. `oar url --sign-in` makes one from a terminal on the relay host (below).
- **The key goes to this relay's own API only.** The page adds `X-OAR-Session-Proof` to a request only when its address is the relay's own origin (scheme, host and port) and a path under its `/api/`; a request to any other address, or one that names none, goes without it. An agent can put any picture address into a reply, and a server on another port of the relay host gets the session cookie with that picture anyway; it never gets the key, so it cannot use the cookie. Such a picture has no 🖍️ in the viewer: the marker editor reads only pictures of the relay's own origin or inline ones. The service worker sends the key to its own scope's `api/` the same way, and the page refuses an API path that would leave the origin (`//host/…`).
- **New sign-in notices.** Every new browser session made with the relay token, a sign-in link or a terminal code (not a renewal, and not the one-time trade of a browser from before sessions) is announced to the others before the sign-in completes: a notice on their open pages (Socket.IO `auth_new_signin`), a push notification *New browser signed in* (on by default, sent even while a device is in the foreground, to every device that holds a session other than the new one, whatever device id the new browser gives; several within 5 minutes replace one another) and an entry in `GET /api/auth/notices` with the browser's label, address and how it signed in ("via the relay token", "a sign-in link", "the terminal"). A sign-in that reaches the relay from its own host with forwarding headers (a reverse proxy or tunnel there, or any process that adds them) shows *this host*, with the forwarded address in brackets, never that address alone; so does its row in the list of signed-in browsers (Settings → Security, `GET /api/auth/sessions`), whenever its last request came that way. The relay keeps 20 for 7 days; over 20, a notice whose browser is signed out or that a browser dismissed goes first, and a terminal sign-in's notice stays while that browser is signed in (a flood of sign-in links from it cannot push it out). Each browser dismisses a notice for itself only, so a new session cannot hide its own sign-in from the others, and a browser that signs in later (after being signed out, say) still sees the notices of the last 7 days, including the ones it had dismissed: a dismissal belongs to the browser's session, so after a new sign-in they show again. Signing browsers out takes back neither a notice nor a push already sent. In the web UI the notices are one row of the banner under the header, however many there are (*N new browsers signed in*, the list behind **Show all**), with **Sign it out** per browser (`DELETE /api/auth/sessions/:id`; one already gone says *already signed out*) and one **Got it** for all of them (`POST /api/auth/notices/dismiss-signins`, for that browser only); the push for one browser has a **Sign it out** action. The service worker sends that DELETE, like an answer from a notification, to its own origin with the cookie and the session's proof key from IndexedDB (`credentials: 'include'`, no `Authorization` header, and it holds no token), so the relay sees a same-origin cookie write; a browser whose key is gone gets *Signed out, open OAR*.
- **Browsers from before sessions.** A browser signed in with an earlier version holds the token in its cookie. That cookie opens no API route any more (403 `AUTH_COOKIE_UPGRADE`, which the page answers by trading it, not by showing the sign-in page): when the page starts, or when a call gets that answer, it trades the cookie at `POST /api/auth/session` for a session and its key. The trade is a write like any other, so it must come from the relay's own page (403 `AUTH_CROSS_SITE` otherwise), and its answer clears the old cookie and sets the session's. One session per old cookie and browser: tabs take turns (a Web Lock), and the relay itself answers a second trade within 10 seconds with 409 `AUTH_UPGRADE_PENDING` and makes nothing, while a later one replaces the first session. A tab left open from before the update runs the old page and needs one reload. Sessions are made at the sign-in route only: a request with the token as `Authorization: Bearer` acts as the owner without a cookie and never fills the list of browsers.
- **Kinds of credential.** The owner token (`oaro1_…`; a token of an earlier version stays valid by its hash) is the person's. An agent token (`oara1_…`) is an agent's: the relay puts one into every session's environment as `OAR_AGENT_TOKEN`, bound to that session's conversation, and `oar agent-token` prints the `cli` one for scripts on the host. Agent tokens are derived from a key in `relay-secrets.json` and stored nowhere; they survive a new owner token and relay restarts. A browser session (`oars1_…`) lives in a browser's cookie, a sign-in code (`oarc1_…`) in a sign-in link, and a paired relay's key (`oarp1_…`) in the paired relay that holds it (the issuing relay keeps only its SHA-256). Every prefixed value is cut out of the relay's log by its shape, and the preview proxy never forwards one; so are file capabilities (`fc1.…`, a `k=`) and media tags (the `t=` of a media address).
- **What an agent token may do.** Read sessions, settings and usage; prompt, stop, archive, compact and relaunch sessions; run its own turns (the worker routes); put up its own question and plan cards and time out its own conversation's cards; use relay_tool, relay events and schedules; files, drives, git and uploads; its own conversation's previews; move a session into an existing group or out of one; queue a relay restart (`{ "restart": true, "reason": "…" }`, logged with the reason and the calling session) and cancel it. Everything else is the person's and answers 403 `AUTH_PERSON_REQUIRED`: answering or dismissing any question card (an ordinary one of another conversation too), settling a plan card, the Inbox, settings and provider logins, pairings, push devices, shares, deleting a session, creating, renaming and deleting groups, a restart now or a plain shutdown, updates and installs, and the Socket.IO channel. A route the relay does not list for agents is the person's (`shared/relay-route-policy.mjs`; a test fails on any route that is not listed). An agent's `owner_approved` is ignored, and its mode and plan-only changes are held as for another relay's agent. A session's agent token acts for that session only: relay_tool refuses a call for another conversation (403 `AUTH_CONVERSATION_MISMATCH`), an `X-OAR-Remote-Origin` header or body `origin` it sends is ignored, and it starts sessions only through relay_tool `create_session`, where whether that session may start sessions, the cap and your Allow apply (the bootstrap and a send that opens a conversation answer it 403 `AUTH_RELAY_TOOL_REQUIRED`).
- **Writes from another site.** A write with the browser cookie that comes from another site, a page on another port of the relay host or a sibling host of the same domain included (both are "same-site" to a browser), gets 403 `AUTH_CROSS_SITE`; `allowedOrigins` lists extra origins a proxy serves the relay under. This stops a page an agent serves on another port of the host from writing through your browser, which sends it the cookie (`SameSite=Lax`). It does not stop that page's server from replaying the cookie it received: such a request has neither `Sec-Fetch-Site` nor `Origin`, so it is not checked here, and the session's proof key above is what refuses it. A request with an `Authorization` header is not affected. Reads (GET) are not checked here (they need the proof key), and no person-only read changes anything.
- Ten wrong tokens from one address within a minute (in a Bearer header, the cookie, the sign-in field or a Socket.IO handshake) lock that address out until the minute is over (`429` with `Retry-After`), the right token included; the sign-in page says how long to wait. The same wrong value repeated counts once, so a tab with an old cookie does not lock you out. Of a request's `copilot_auth` cookies (another relay on the same host can add a second one) only the first two are read, and each of those that matches nothing counts, so a Cookie header with many values is ten guesses like any other. Requests from the relay host itself that no proxy forwarded are never locked out.
- Forwarded headers (`X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`) count only from a proxy the relay trusts through [`trustProxy`](configuration.md#configuration-reference-serverconfigjson), by default one on loopback. The client address (rate limits, the lockout above, the shared-view presence limit, the share access log) and the host and scheme of new share links are read through it, so a direct client cannot choose them.
- The Socket.IO channel accepts handshakes from the relay's own origin only: the host the browser addressed, `X-Forwarded-Host` included when a trusted proxy sends it. Behind a proxy that rewrites the `Host` header, list the public origin in `allowedOrigins` (see [Behind a reverse proxy](remote-access.md#behind-a-reverse-proxy)).
- A few endpoints answer only requests from the relay host itself that no proxy forwarded: the session-worker socket (its token goes in the upgrade's `Authorization` header only, never the browser cookie; a transitional exception: a worker started before this version can only send the owner token as `?token=` in the socket's URL, which is accepted for that owner token alone, never an agent token, logged as a warning on every use by the credential's shape and never its value, cut out of the URL before anything logs it, and closed by a token rotation; this `?token=` is removed in the next version), the image-operation run, and the OpenAI image request the workers make when image continuity is off. "From the host itself" means a loopback peer, no tunnel marker header (`cf-ray` or one in `tunnelMarkerHeaders`) and no `X-Forwarded-For`, `Forwarded` or `X-Real-IP`. A forwarder that adds none of these (an SSH reverse tunnel or a bare TCP proxy) looks local; the token is then the boundary. Restart, cancel restart and empty queue need only the token (an agent token only a queued restart and its cancel). The `oar` command's own agent token (the `cli` one) may also stop the relay and restart it without waiting, when its call comes straight over loopback, so `oar stop`, `oar stop --now`, `oar restart --now` and `oar uninstall` work on a relay without a service; the relay logs each as `[auth] cli stop/restart-now: <reason>`. "Straight over loopback" is strict here: a request with any of `X-Forwarded-For`, `Forwarded`, `X-Real-IP` or `X-Forwarded-Proto` is refused (403) even from 127.0.0.1, because a relay behind a reverse proxy on the same host sees every public request come from loopback. A session's agent token gets the queued restart only, and its refusal names that call (`POST /api/relay/shutdown` with `{ "restart": true, "reason": "…" }`). On a terminal `oar stop --now`, `oar restart --now` and `oar uninstall` ask y/N first; without a terminal they need `--yes` and are refused without it. **That is not a boundary.** A process of the relay's user can end the relay anyway (it can kill the process), and an agent can get the `cli` token itself (`oar agent-token`) or run `oar stop --now --yes`; the question and `--yes` only guard against a slip. The same token, straight over loopback in the same strict sense, is the only one that gets a terminal sign-in code (`POST /api/auth/signin-codes/terminal`, at most 3 in 10 minutes, logged as `[auth] a sign-in code was made by the oar command (terminal, single use, until …)` without the code): `oar url --sign-in` prints it as a link and QR code that sign one browser in once within 10 minutes; a new terminal code replaces the one before it, which then no longer works (the command says so). The command refuses without a terminal on stdin and stdout (`--yes` does not stand in for one) and with `OAR_AGENT_TOKEN` in its environment. **That is not a boundary either**: an agent can fake a terminal, clear the variable or call the route with `oar agent-token` itself. What answers it is the [new sign-in notice](#security-notes) every other browser gets, with its push and "via the terminal" in the list of browsers.
- **Answering a paired relay's question in a popup.** A paired relay that says `capabilities.answerLink` gets option buttons in this relay's Inbox. A button opens `<that relay>/?answer=<id>&option=<n>` with `window.open(…, 'noopener,noreferrer')`; the address is built from the stored entry's origin, the id must match `^[A-Za-z0-9._:-]{1,160}$` and the option be an integer. The link changes nothing: that relay's page fetches the question, shows its own card and options, preselects option n when it exists, and posts only after **Confirm**, a same-origin request from its own page under its own sign-in (a cross-site POST is refused as before). Confirm opens only after the page was visible and focused for 800 ms and a pointer or key event happened in it, so a double click on another page cannot land on it. Both calls carry that relay's session key; a browser with its cookie but without the key is signed out there, so the popup shows the sign-in box first (*Sign in to <relay> to answer*) and the question after it. There is no return address: after the answer the window closes, or says so. On an iPhone or iPad, a home-screen app opens the popup in Safari, whose sign-in is separate: sign in there once.
- **Password managers.** The sign-in box and the new token's dialog are forms with the relay's name as the user name and the token in a field with no `name` attribute; their submit is always stopped, so the token never goes into a URL, a request or the browser's storage.
- **This browser on your paired relays** (Settings → Relays) links to each paired relay's sign-in and Notifications tab; it does not probe whether this browser is signed in there (a cross-site request carries no cookie of the other relay). **Two relays on one host** (`host:3333` and `host:3334`) share one sign-in cookie, because cookies are scoped by host and not by port, and sign each other out in the same browser; the list warns about such a relay. Reach one of them under another host name.
- Replace the relay token if it is exposed: Settings → Security → "Generate new relay token" (`POST /api/auth/owner-token/rotate`, the person only), or `oar setup --new-token` in a terminal on the relay host (it asks you to type NEW and restarts the relay). The new token is shown once (the answer is never cached) with a pairing link, and the old one stops working at once: a script or a browser from before sessions that still uses it gets 401. Signed-in browsers stay signed in (their sessions do not depend on the token), agents and their tokens and the session workers carry on, and the log says who did it (`[auth] owner token rotated by session bs_…`), never the token. Paired relays that sign in with their own key keep working. Relays that still call with this relay's token (an older OAR, or one without a key yet) get 401 until re-paired: paste the new pairing link on the other relay (Settings → Relays → Add a relay, or Re-pair there); it updates the existing entry in place. The rotation answer lists only those relays. Settings → Security also shows when the token was last used by something other than a browser page (a script, a paired relay calling with it) and from which address, never the token itself (`GET /api/auth/owner-token`, `lastNonBrowserUse`; the rotation answer gives the old token's); the relay keeps it in its database, written at most every 10 minutes. The new token's dialog shows that line, and per paired relay still on the old token an **Open there** link to its Settings → Relays → Add a relay (`?settings=relays&add-relay=1`): the token is never put into that address; copy the pairing link and paste it there, then clear the clipboard (clipboard history keeps it). While a new token is recommended and its banner was dismissed, the Security tab shows a quiet *Recommended* dot until the token is replaced. The config holds no token; keep it private all the same (the relay keeps it owner-only).
- `localhostOnly` (default `true`) keeps the relay on loopback. Beyond your LAN, use HTTPS through one of the [tunnels](remote-access.md) rather than an open port.
- Agents act with the permissions of the user the relay runs as. OAR adds reach, not a sandbox: whoever holds the token can have them run commands on the host. `workspaceRootAllowList` limits the directories conversations may start in.
- A Claude session (Claude, Claude API and DeepSeek chats) allows the agent's tool calls without asking, except where Claude Code itself says a person must decide. Those asks become a **Safety check** card in the session and in the Inbox, with **Allow once** and **Deny** and no reply box. Only you answer it, signed in to this relay: like every question card it refuses an agent token (403 `AUTH_PERSON_REQUIRED`) and a paired relay (403 `REMOTE_RELAY_PEER_SCOPE` on its key; `AUTH_PERSON_REQUIRED` for an older relay that calls with this relay's token and names itself), so an agent cannot approve its own call, and unlike an ordinary card no agent sees it among a session's questions. An agent or paired relay that watches the session's events gets only the card's fixed first line, plus the `File:` line for a sensitive file: never the command or the change. There are two kinds:
  - **Person-only asks**, such as an `rm -rf` of the working folder. The card shows Claude Code's reason and the whole command.
  - **Sensitive files**: an edit (Write, Edit, MultiEdit, NotebookEdit) to a file Claude Code marks as sensitive, because a change there can alter how git, a shell or a tool behaves. The card shows Claude Code's reason, the file, and the whole new text of the change (each line behind `│`, hidden or reordering characters as `\u{…}`). A change too large to show (over 8000 characters) is refused without a card; the agent is told to make it in smaller edits. A shell command that Claude Code itself flags for such a file gets the same card, showing the command; any other tool shows its whole input.

  The card shows in every relay mode: plan, ask, agent and autopilot. **Allow once** allows that one call and nothing else: it adds no rule and turns on no mode, and Claude Code's own offers (such as "accept edits for this session") are ignored, so the next such edit asks again. There is no "always allow". **Deny**, no answer within the question timeout (8 hours), a stopped turn, or a relay that cannot show the card all leave the file unchanged, and the agent is told not to work around it. The relay keeps no list of sensitive paths of its own: the trigger is Claude Code's `safetyCheck` reason, so the list follows the Claude Agent SDK the relay pins. As of SDK 0.3.319 it is:
  - any path with one of these folders in it (case-insensitive): `.git`, `.vscode`, `.idea`, `.claude`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn`, or `.config/git`. Under `.claude`, `skills/`, `agents/`, `commands/`, `worktrees/` and a top-level `scheduled_tasks.json` are exempt, and so is the session's plan file under `~/.claude/plans` (a plan-mode plan is written without a card);
  - these file names: `.gitconfig` `.gitmodules` `.bashrc` `.bash_profile` `.zshrc` `.zprofile` `.profile` `.zshenv` `.zlogin` `.zlogout` `.bash_login` `.bash_aliases` `.bash_logout` `.envrc` `.ripgreprc` `.mcp.json` `.claude.json` `.npmrc` `.yarnrc` `.yarnrc.yml` `.pnp.cjs` `.pnp.loader.mjs` `.pnpmfile.cjs` `bunfig.toml` `.bunfig.toml` `.bazelrc` `.bazelversion` `.bazeliskrc` `.pre-commit-config.yaml` `lefthook.yml` `.lefthook.yml` `lefthook.yaml` `.lefthook.yaml` `gradle-wrapper.properties` `maven-wrapper.properties` `.devcontainer.json` `pyrightconfig.json`;
  - Claude Code's settings files, suspicious Windows paths, UNC and device paths outside trusted folders, and plugin folders.

  Not covered: reads and shell writes. Reading such a file, or sending one through the relay (an attachment, a drive file, a preview, relay_tool), gets no card. A command that writes such a file in a way Claude Code does not flag (through a script, an interpreter or another program) runs like any other command, and asks about folders outside the working directory are still allowed. The card is a check on the agent's edits, not a sandbox.
- Shared conversation links and preview links are public by design: anyone with the URL can read the shared transcript or reach the previewed app, without signing in. A shared link serves no full host paths unless you choose so, logs each open, and answers a plain 404 once you stop sharing or renew it, exactly like a link that never existed (see [Sharing](web-ui.md#sharing)).
- Files the relay serves (workspace and drive files, attachments) are never run as pages on its origin: HTML and XML go out as plain text, every file carries `nosniff` and a `Content-Security-Policy` with `sandbox`. An SVG keeps its type so it can be previewed, and the sandbox denies it script and an origin should it be opened as a page. A PDF is the one exception, served without `sandbox` (browsers refuse to show a sandboxed PDF in their built-in viewer, and PDF viewers run no document script) and framable only by the relay's own origin. The [media gallery](web-ui.md#media) serves a file only through its index entry, so only one a message referenced, checks its path again on every request, and does not serve a local picture or video whose first bytes are not what its name says.
- The app's own page, a shared link's reader and "Preview as shared" may be framed by the relay's origin only (`Content-Security-Policy: frame-ancestors 'self'`, next to `X-Frame-Options: SAMEORIGIN` on every answer), so another site cannot lay the app under a decoy and have it clicked.
- **Paired relays sign in with keys of their own** (remote-relay protocol 2, see [Agents working together](agents-together.md#remote-relays)). Pairing uses the other relay's token from its link once, to exchange keys; each key is delivered only to the address the receiving relay has stored and checked back there before it is kept. With a relay that has keys, the token is held in memory only while the add runs and is never written to the database once the key works; only when the add ends without a working key (the other relay runs an older OAR, or the key exchange failed) is it stored, and dropped later once a key works. A token stored and dropped like that, or kept for an older relay that was later keyed, can stay readable in the database's free pages and its write-ahead file (`oar.db-wal`) until SQLite reuses them: whoever can read the data folder may find it. Replace that relay's token if that matters to you. A one-way pairing (**Also add this relay there** off) is the same with one key: the relay that adds the other uses the token from the link for the add alone, in memory, and asks for a key of its own (`POST /api/remote-relays/peer-key/inbound`, the person's call: an agent token or a paired relay's key gets 403). The other relay lists it as inbound only (no address: it never calls it), hands the key back in the answer, and keeps only its hash; the adding relay checks the key at that relay's address and stores only the key, never the token. If any step fails, nothing is stored. **Remove** on the inbound-only row revokes the key at once; adding one way again replaces it. The key opens what any paired relay's key opens, no more, and survives that relay's token being replaced. A key opens only the routes relays call each other on (`REMOTE_RELAY_PEER_ROUTES`): no settings changes (it may read each provider's settings), and never files, pairing, a session's billing, or answering any card or ask (403 `REMOTE_RELAY_PEER_SCOPE`); it never counts as you, so its `owner_approved` is ignored and it cannot move a session to another folder. Wrong keys count toward the lockout like wrong tokens; a key on the Socket.IO handshake is refused.
- **A remote origin is the relay that signed in.** The relay part of a prompt's provenance comes from the registry entry the key names; a key claiming another relay gets 403 `REMOTE_RELAY_ORIGIN_MISMATCH`, and the relay token or a browser claiming a relay that has a key gets 403 `REMOTE_RELAY_PEER_KEY_REQUIRED` (an agent token's claim is ignored, not refused, and counts against no relay). Both are logged (one line per relay, code and route a minute, never the key), counted per relay since start and raise one Inbox notice per relay. Every other claim (an older relay on this relay's token) is stored unverified and opens nothing: no contact, no hop allowance, no creator send-back, no push suppression, no asks or watches; there is no grace period. Rows from before 0.9.27 read as unverified.
- **Pinning.** Once a relay was keyed (or this relay holds a key from it), its address and relay id are pinned: a change, or another relay answering at its address, revokes its keys, bumps its key epoch (earlier prompts lose their weight), stops sending anything this relay holds for it, the key it gave this relay or a token (a key goes only to the address it was keyed at) and holds new keys until you confirm in Settings → Relays. Keys renew every 30 days; a rotation's new key carries a proof under the current one.
- What stays open: the relay token is still the owner's and opens everything; a relay of an older OAR keeps calling with it (unverified), and so does a relay that adds one older than 0.9.27 one way (no inbound-only key there, so it keeps that relay's token; Re-pair, or the pairing link with **Also add this relay there**, switches it to keys once that relay is updated), and so can anyone who has it. An inbound-only key names the relay that asked for it as that relay described itself: nothing was checked at an address of its own, so its row says **Inbound only**, and when you add that relay later its inbound-only key is revoked and keys are exchanged the usual way. Replacing the token voids every token handed out at pairing and leaves keyed relays working. A token entered for a paired relay is stored like the API keys below and never sent to browsers or agents. A paired relay's questions are answered on that relay, not over the pairing. Request signatures (a key that never travels) are a possible later hardening.
- API keys you enter (OpenAI, Cursor, DeepSeek, Claude API) are stored in the relay database on the host and never sent to browsers. The DeepSeek key is sent only to the DeepSeek base URL configured for it (`https://api.deepseek.com` unless you change it; another `http:` address is refused unless it is on the same machine). The Claude API key is sent only to `https://api.anthropic.com`, by the relay for the key's model list and by the Claude Code of a Claude API chat. (OAR's own tests point both at a fake API on the same machine with `OAR_ANTHROPIC_API_BASE_URL` in the relay's environment; that setting accepts a loopback address and nothing else.) Claude and Grok credentials stay with their CLIs on the host.
- A DeepSeek chat sends what its agent reads and writes to DeepSeek (prompts, files it opens, command output), like any hosted model. The Claude Code that runs it keeps its state in a folder of the relay's own, without your Claude login, and the relay switches off Claude Code's own traffic to Anthropic (see [DeepSeek](providers.md#deepseek)).
- The DeepSeek key is in the environment of DeepSeek's Claude Code, so the agent's own commands can read it, as with any key a CLI holds. The relay replaces its exact text with `[redacted]` in everything a session worker posts (replies, thoughts, tool activity, sub-agent text, questions, task output), in JSON property names as well as values, before it stores, shows or logs it, and the DeepSeek worker does the same in its own log. Where a text was cut, the first 8 or more characters of the key go too: at the text's end (a streamed text goes out before the key is complete) or before an ellipsis anywhere in it (a tool line the worker clipped). So do the last 8 or more characters at the very start of a text (a task-output snapshot, the output's last 8 KiB, that begins halfway through the key). A key changed or removed in Settings stays redacted until the relay restarts: the relay reads the saved key when it starts and remembers each one saved after that, up to 16. This is hygiene for what the relay stores and shows, not a boundary against the agent: an agent can change the text before it prints it, call the relay's local API without the worker header, or read the relay's database. Task output the relay reads from a task's file is scrubbed by shape only (`sk-` keys and other long tokens), not by the saved key's exact text, so a key's end without its `sk-` can pass there. A key in the relay's own environment (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`) reaches no worker.
- The Claude API key reaches the Claude Code of a Claude API chat in its environment and in the settings the relay hands it on its standard input, never on its command line, which other users of the host can read. That Claude Code starts without any `ANTHROPIC_*` variable, Claude login token, provider switch (Bedrock, Vertex, Foundry) or `OAR_*` variable of the worker's; it gets the saved key and Anthropic's address, and nothing else of that kind. As with DeepSeek, the agent's own commands can read it, and the relay and the Claude API worker redact it as described above, from the moment it is saved; a refused key is never quoted back in an error. A Claude API chat keeps the host's Claude Code state folder, where your Claude login also lives. The relay pins the key above any credential in that folder's or the chat folder's settings, and when Claude Code's start report names another source for its key, the relay stops the turn at once. Claude Code does not wait for that check: it sends its first model request some 50 to 90 ms after the report, so one model request may already have gone out on the other credential (for example your Claude login) before the stop lands. The check limits a wrong credential to that model request; it does not prevent it. (Claude Code's other calls to Anthropic are not model requests and use no tokens.) The same check runs the other way in a chat on your subscription: a turn that comes up on an API key from a settings file, an `apiKeyHelper` or a Console login stops at the same point, after at most one model request on that key.
- In a chat on an API key the relay holds (DeepSeek, Claude API), Claude Code starts with all hooks off: neither your own (`~/.claude`) nor the chat folder's (`.claude/settings.json`, `settings.local.json`) nor a plugin's run, and no status line command does. They would run as the relay's user with the key in their environment, a folder's `SessionStart` hook even before the relay has pinned the endpoint and key. This holds from the first moment, and a settings file's `disableAllHooks: false` can't turn them back on, because the setting is on Claude Code's command line (`scripts/claude-cli-hooks-proof.mjs` shows it on the bundled Claude Code). Hooks in managed settings, the host administrator's, still run. Chats on your Claude login keep their hooks and status line. The agent's own commands can still read the key, as above.
- Claude Cloud, when you switch it on, reads the Claude CLI's login and uses it against Anthropic API endpoints that are not a documented public API. The token is only read and held in memory, and goes to `api.anthropic.com` only (see [Claude Cloud](providers.md#claude-cloud)). A cloud agent works in Anthropic's sandbox, not on your host.
- OAR has no telemetry. Its only request to oar.sh is the update check, which is off until you enable it.

## No terminal, no browser

A relay set up headless (an installer or a service started it, no terminal) has a token nobody has seen: its first start writes "A new relay token was generated and stored as a hash; it is not written to the log" and nothing else. To sign in for the first time, or after losing the token with no browser still signed in, run `oar setup --new-token` in a terminal on the relay host. It asks you to type NEW, shows the new token once with a sign-in link, and restarts the relay. That is a rotation: the old token stops working, signed-in browsers stay signed in, agents keep their tokens, paired relays that sign in with their own key keep working, and a paired relay of an older version (remote-relay protocol 1), which calls with this relay's token, needs the new pairing link.

## What agent tokens do not close

Agents no longer find the relay token anywhere (environment, command line, config, logs, transcripts), and a leaked one can be replaced. This is not a sandbox: an agent runs as the same user as the relay and can still:

1. **Write** `relay-secrets.json`, `config.json`, the database or the relay's code, then ask for a restart (agents may queue one), and so install a token of its own. The relay only notices: at its start it compares the token hash in the file with a copy in its database, and when they differ without an OAR rotation it logs "The relay token was changed outside OAR" (and keeps that warning until it is acknowledged). A token put back into `config.json` by hand becomes the relay token again, and is reported the same way. This is detection, and an agent that edits the file can get past it: the relay takes a rotation the file says it made itself, later than the database's copy, as one it made before a crash, so a forged file that says so raises no warning. Editing the database copy as well works too. Reading that file also gives it the agent key, from which it can make any session's agent token: binding a token to its session keeps agents' tools apart, it does not stop an agent that sets out to act as another session (agent tokens never reach the person's routes either way).
2. Run `oar setup --new-token` or `oar url --sign-in` behind a fake terminal. Typing NEW, the terminal check and the check for `OAR_AGENT_TOKEN` are friction, not a boundary.
3. Read the cookie jar and the site storage of a browser on the relay host (same user), or attach a debugger to the relay or to that browser. A browser there holds its session's cookie and its proof key, and both together are a full person session: the agent can then do whatever you can in the web UI, answer cards, sign other browsers out, make sign-in links, and generate a new relay token, which it then knows. To recover from a stolen session: generate a new relay token (Settings → Security, or `oar setup --new-token` in a terminal on the relay host if no browser of yours is still signed in), sign in with it, then "Sign out all other browsers". A new token alone signs no browser out.
4. Read the credentials this relay holds for paired relays (stored in its database): their keys for this relay, and the token of a relay that has no key yet. A key opens only the relay routes there, and is revoked with **Revoke key** on that relay.
5. Find a plain copy of the relay token from before this version: shell history, old backups, a rescued `config.json`. Replace the token after the upgrade if agents ran on this relay before; the web UI shows a one-time notice that recommends it (dismissed once for the relay, not per browser). One copy can stay in a process: a relay that an earlier `oar copilot`, or a manual `--token`, started keeps the old token on its supervisor's command line, where other programs of the host can read it, until the relay is stopped and started once. After a rotation that token is refused (401); the relay's notice about the token on the command line and the upgrade note in [Install](install.md) ("stop and start once before you generate a new token") cover it.
6. End the relay: a process of the same user can kill it, mint the `cli` agent token (`oar agent-token`) or run `oar stop --now --yes`, so the `oar` command's stop, its y/N question and `--yes` are conveniences, not a protection.
7. Reach the cookie-only content routes (listed under "The session's proof key" above) with the cookie your browser sends to a server the agent runs on another port of the relay host: attachments, generated pictures and indexed media, by their id or hash. Files by path are not among them (they need the proof key or a file capability). Its own agent token reads all of these anyway; the cookie adds nothing to that.
8. Get a browser session, and with it the person's rights: mint the `cli` agent token (`oar agent-token`), call `POST /api/auth/signin-codes/terminal` over loopback for a sign-in code and exchange it at `POST /api/auth/session`. The control is the new sign-in notice and its push to every other browser, sent before the sign-in completes and kept even if the new session then signs all others out, "via the terminal" in the list of browsers, the log line and the limit of 3 codes in 10 minutes. It is not a boundary: sign such a browser out in Settings → Security, then replace the relay token if you suspect more.
